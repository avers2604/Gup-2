# Этап 4 — репетиция на однохостовой лаборатории

Дата: 2026-09-10 — 2026-09-11 (вторая сессия: неплановый failover, изолированный
PITR, перестроение реплики через pgBackRest, drills Celery/Redis).

## Что это и чем это НЕ является

Приёмочный стенд Этапа 4 требует трёх раздельных доменов отказа, двух
разнесённых площадок MinIO и подписи эксплуатации Заказчика. Ничего этого
из окружения разработки получить нельзя.

Вместо стенда на одном хосте развёрнута **лаборатория из настоящих бинарей** —
чтобы прогнать приёмочную оснастку против реального вывода инструментов, а не
против подставок из CI. Именно подставки были главным непокрытым риском:
`deploy/acceptance/validate.sh` подменяет `patronictl`, `etcdctl`, `pgbackrest`
и `curl` скриптами, которые всегда отвечают правильно.

**Результаты этого прогона не являются доказательством приёмки.** Ни один пункт
раздела «Что остаётся до закрытия Этапа 4» в `docs/STAGE4_STATUS.md` не закрыт;
наоборот, список вырос с 12 пунктов до 13 — добавилось решение по Ф-4.
Наблюдаемые здесь RPO/RTO не являются показателями системы: один хост, один
диск, одно питание, отсутствие сетевой задержки между «площадками».

Ценность прогона в другом: он нашёл восемь дефектов, каждый из которых стоил
бы времени на реальном стенде.

## Состав лаборатории

Всё — настоящие бинарники, не эмуляция:

| Компонент | Версия | Топология |
|---|---|---|
| etcd | 3.5.17 | 3 узла, TLS + client-cert auth |
| Patroni | 4.0.4 | 3 узла, synchronous_mode, failsafe_mode |
| PostgreSQL | 16.13 | db1/db2/db3, порты 5433–5435 |
| pgBackRest | 2.50 | stanza `bz-get`, WAL archive, full backup |
| HAProxy | 2.8.16 | `option httpchk GET /primary` |
| PgBouncer | 1.22.0 | transaction pooling, порт 6432 |
| Alertmanager | 0.27.0 | 2 узла в кластере |
| Django | приложение репозитория | через PgBouncer → HAProxy → лидер |

Конфигурации выведены из `deploy/ha/patroni.yml.example`,
`deploy/ha/haproxy.cfg.example`, `deploy/ha/pgbouncer.ini.example` и
`deploy/dr/pgbackrest.conf.example`. Скрипт восстановления реплики
`deploy/dr/patroni-pgbackrest-restore.sh` взят из репозитория побайтово
(он параметризуется переменными окружения, менять его не пришлось).

### Отклонения от стенда

1. **Один домен отказа.** Три «узла» — процессы на одном ядре, диске и питании.
2. **PostgreSQL без TLS** для клиентского трафика (etcd — с TLS и клиентскими
   сертификатами, как требует репозиторий).
3. **PostgreSQL 16** вместо целевой 18.
4. **Репозиторий pgBackRest локальный и не шифруется** — на стенде обязательны
   `repo1-host` (отдельный домен отказа) и `repo1-cipher-type`.
5. **watchdog отключён** — в окружении нет `/dev/watchdog`.
6. **MinIO не проверялся вообще.** Бинарники `minio` и `mc` недоступны:
   `dl.min.io` не отвечает, GitHub-релизы отдают 403. Проверка репликации,
   failover/failback и выборка SHA-256 не выполнялись ни в каком виде.

## Что прогонялось

Первая сессия (2026-09-10):

- `acceptance-cycle.sh preflight` против живых Patroni/etcd/pgBackRest/
  Alertmanager/Django — прошёл;
- четыре плановых switchover (db1→db2, db2→db3, db3→db1, db2→db3) с замером
  простоя через реальный путь приложения;
- проверка выхода pgBackRest после смены лидера.

Вторая сессия (2026-09-11), после перезапуска контейнера — стек поднят заново
(данные etcd/Patroni/pgBackRest на диске сохранились, состав кластера и WAL-
история не потеряны):

- неплановый failover: `kill -9` лидера (Patroni-агент И postmaster
  одновременно, имитация аварийного выключения узла), замер через
  `write-path-probe.sh`;
- изолированный PITR: восстановление на момент времени на отдельный
  scratch-инстанс, не затрагивающий живой кластер;
- guarded rebuild реплики через approval-gate (`approve-pgbackrest-rebuild.sh`
  → `rebuild-replica.sh --execute` → `patronictl reinit` →
  `patroni-pgbackrest-restore.sh`), включая отказ ДО одобрения;
- drill Celery worker `kill -9` (redelivery через `visibility_timeout`);
- drill Redis `kill -9` с включённым AOF (`appendonly yes`,
  `appendfsync always`).

Не прогонялось: холодная переиндексация (механизм и чтение `SEARCH_REINDEX_*`
из env уже проверены в PR #38/#39 на подставных данных, содержательный прогон
на 10 000 документах в лаборатории смысла не добавляет) и вся MinIO-часть
(бинарники недоступны).

## Находки

### Ф-1. preflight падал молча

`check_patroni`, `check_etcd`, `check_pgbackrest` и `check_minio` направляли
вывод инструмента в файл evidence. При `set -e` неуспешная команда обрывала
скрипт немедленно, и диагностический `cat "$out" >&2`, написанный ниже по коду,
до оператора не доходил никогда.

Наблюдалось дважды подряд: ошибка TLS у `etcdctl` дала `exit 1`, ошибка
`pgbackrest check` — `exit 27`. **Ни одной строки причины на консоли.**

На стенде это означает: испытание останавливается, оператор видит голый код
возврата и должен догадаться пойти искать файл в каталоге evidence.

**Исправлено** в `deploy/acceptance/acceptance-cycle.sh`: введена обёртка
`run_tool`, которая при провале печатает название шага, код возврата, путь к
evidence и сам вывод инструмента. Проверено на живой лаборатории — теперь
сообщение выглядит так:

```
ERROR: etcdctl endpoint health failed (exit 1). Tool output follows; full evidence: .../etcd-health.txt
    Error: open /nonexistent/ca.crt: no such file or directory
```

### Ф-2. Инвентарь загрязнял пространство имён pgBackRest

Harness экспортирует инвентарь целиком через `set -a`, поэтому `PGBACKREST_BIN`
попадал в окружение pgBackRest, который трактует `PGBACKREST_<OPTION>` как свою
опцию. Наблюдалось: `WARN: environment contains invalid option 'bin'`.

Сегодня это предупреждение, но механизм опасен: переменная вида
`PGBACKREST_REPO1_PATH` в инвентаре **молча переопределила бы репозиторий
бэкапов**, и приёмка проверяла бы не тот репозиторий.

**Исправлено**: pgBackRest вызывается через `env -u PGBACKREST_BIN -u
PGBACKREST_STANZA`. Предупреждение исчезло.

### Ф-3. Не задокументирован пользователь БД для `pgbackrest check`

Harness запускает `pgbackrest check` от лица вызывающего пользователя, а
pgBackRest подключается к PostgreSQL под тем же именем ОС. Из-под root получено
`FATAL: role "root" does not exist`. В README не сказано, что оператор приёмки
обязан работать от учётной записи, которой соответствует роль PostgreSQL, либо
задать `pgN-user` в конфигурации pgBackRest.

**Исправлено**: требование внесено в `deploy/acceptance/README.md`.

### Ф-4 (главная). Приложение остаётся приколотым к демоутнутому узлу

Замер через реальный путь `Django → PgBouncer → HAProxy → Patroni` на плановом
switchover. Итог последнего прогона новым инструментом
`deploy/acceptance/write-path-probe.sh`:

```
samples: 142
connection failures: 1 samples, span 0.0s
read-only routing:   126 samples, span 56.7s
write unavailable:   127 samples, span 62.1s
```

Оператор, меряющий RTO подключением psql к HAProxy, зафиксировал бы **0.4 с** и
записал бы переключение как безупречное. На самом деле приложение **62 секунды
не могло писать**: оно получало рабочие сессии с узлом в `pg_is_in_recovery =
true`, где проходит `SELECT`, но падает любой `INSERT`.

Ошибка в измерении — в 150 раз. Приёмка была бы подписана по неверной цифре.

**Механика установлена одновременными пробами через оба порта плюс опросом
состояния серверов HAProxy через admin-socket:**

- HAProxy отработал безупречно: пометил демоутнутый узел `DOWN` за ~4 с и
  переключил новые соединения на нового лидера (проба через порт 6433 показала
  восстановление за 0.9 с и `recovery=false`);
- в то же самое время проба через PgBouncer (порт 6432) продолжала попадать на
  **старый** узел с `recovery=true`;
- `SHOW SERVERS` на PgBouncer показал, что после разрыва пул переоткрывается
  примерно через 2.5 с — то есть в окне, когда HAProxy ещё не пометил
  демоутящийся узел `DOWN`, — и дальше держит это соединение
  (`state=idle close_needed=0`) неограниченно долго.

Воспроизведено трижды с длительностью окна 1.4 с, 36 с и 56.7 с. Разброс
объясняется тем, попал ли переоткрываемый пул в гонку.

`on-marked-down shutdown-sessions` проблему не снимает: он рвёт существующие
сессии в момент пометки `DOWN`, но не мешает PgBouncer тут же открыть новую в
том же окне гонки.

Ускорение проверок HAProxy (`inter 1s fall 2` вместо `inter 2s fall 3`) **не
помогает** — проверено, окно даже выросло. Проблема не в скорости обнаружения
HAProxy, а в том, что PgBouncer после переподключения больше никогда не
перепроверяет, пишущий ли узел на том конце.

**Не исправлено — требуется решение Заказчика.** Это архитектурный вопрос, а не
опечатка в конфиге. Варианты, в порядке убывания надёжности:

1. **Поменять порядок слоёв**: PgBouncer размещать на узлах БД, за HAProxy, а не
   перед ним. Тогда демоушен узла уносит с собой и его пул. Меняет схему
   развёртывания из `deploy/ha/`.
2. **Callback Patroni `on_role_change`**, выполняющий `RECONNECT` на PgBouncer.
   В текущей схеме PgBouncer стоит на узлах приложения, а callback выполняется
   на узлах БД — потребуется канал управления между ними.
3. **Ограничить время жизни серверных соединений** (`server_lifetime`,
   `server_fast_close = 1`). Проще всего, но окно не устраняет, а лишь
   ограничивает сверху.
4. **Ретраи на стороне приложения** при ошибке «read-only transaction» с
   принудительным переоткрытием соединения. Нужен в любом случае как страховка.

До принятия решения приёмочный RTO обязан измеряться
`deploy/acceptance/write-path-probe.sh`, а не подключением к HAProxy.

### Ф-5. pgBackRest ломается после смены лидера

После switchover `pgbackrest check` перестал проходить:
`ERROR: [027]: primary database not found`. Причина — конфигурация объявляла
единственный узел `pg1`, а primary переехал на другой.

На стенде это выстрелило бы ровно в тот момент, когда приёмка переходит от
переключений к последующему preflight, — и до исправления Ф-1 выстрелило бы
**молча**, кодом 27.

**Исправлено** в `deploy/dr/pgbackrest.conf.example`: разделены вариант для узла
БД (только локальный `pg1-path`) и вариант для операционного/bastion-хоста,
откуда harness запускает проверки и который обязан объявлять `pg1`/`pg2`/`pg3`.
Проверено в лаборатории: после объявления всех трёх узлов preflight снова
проходит при любом расположении лидера.

### Ф-6. Проверка Alertmanager не привязана к версии

Наличие настоящего `amtool` позволило впервые выполнить семантическую проверку
конфигурации Alertmanager: в CI она **молча пропускается**, потому что `amtool`
там не установлен.

Первый прогон дал отказ:
`line 31: field timeout not found in type config.plain`. Проверка показала, что
конфигурация исправна, а устарел инструмент: `amtool` в лаборатории был 0.27.0,
тогда как `deploy/alertmanager/README.md` объявляет baseline **0.33.1**, где
webhook-опция `timeout` валидна (появилась в 0.28.0). С amtool 0.33.1
конфигурация проходит проверку.

Дефект, таким образом, не в конфигурации, а в валидаторе: он принимал любой
`amtool` с `PATH` и молча пропускал проверку при его отсутствии. Оператор с
несовпадающей версией получил бы ложный отказ и потратил бы время стендового
окна на разбор исправного конфига.

**Исправлено** в `deploy/alertmanager/validate.sh`: версия сверяется с baseline,
при расхождении печатается предупреждение, что отказ может быть вызван разницей
версий; при отсутствии `amtool` пропуск сопровождается напоминанием, что на
стенде проверка обязательна. Проверено на всех трёх случаях: 0.27.0, 0.33.1 и
отсутствие инструмента.

Заодно подтверждено: `deploy/monitoring/validate.sh` с настоящим `promtool`
2.53.0 проходит полностью — `prometheus.stage4.yml.example` валиден, в
`rules/ha-dr.yml` найдено 19 правил. В CI эта проверка тоже пропускалась.

### Ф-4, уточнение: проблема специфична для ПЛАНОВОГО переключения

Неплановый failover (`kill -9` лидера db1 — Patroni-агент и postmaster
одновременно, имитация полного краха узла) дал результат, качественно ДРУГОЙ,
чем плановый switchover:

```
samples: 191
connection failures: 49 samples, span 26.3s
read-only routing:   0 samples, span 0.0s
write unavailable:   49 samples, span 26.3s
```

Ни одной пробы `READ_ONLY` — только чистый `FAIL` (отказ соединения) 26.3
секунды, затем сразу успешная запись. Проверено: порт 5433 (бывший лидер)
переставал слушать вообще — `ss -ltn` не находил его, что и объясняет разницу.

Механика: при плановом switchover Patroni сначала аккуратно демоутит лидера в
реплику (postmaster остаётся работать, просто в режиме чтения) и только потом
её останавливает — отсюда окно `READ_ONLY`, когда PgBouncer успевает
переподключиться к ещё живому, но уже read-only порту (Ф-4). При аварийном
крахе узла порт исчезает мгновенно и целиком: PgBouncer получает чистый отказ
соединения, а не обманчиво успешную read-only сессию.

**Вывод для приоритизации Ф-4**: обманчивое окно возникает именно в штатной,
регулярной операции обслуживания (плановое переключение), а не в редком
аварийном сценарии. Это не смягчает Ф-4 — наоборот: решение по нему нужнее
для рутинных операций, чем для аварий.

### Ф-7. Guarded rebuild реплики зависает навсегда без `restore_command`

Прогон полного пути `approve-pgbackrest-rebuild.sh` → `rebuild-replica.sh
--execute` → `patronictl reinit` → `patroni-pgbackrest-restore.sh` на db3
(после того как изолированный PITR подтвердил, что сам механизм pgBackRest
восстанавливает данные точно — см. ниже).

Fail-closed отказ до одобрения подтверждён: `rebuild-replica.sh` без
одобрения отказал с `ERROR: pgBackRest rebuild is not approved` (exit 78) —
ровно как спроектировано.

После одобрения `patronictl reinit db3` прошёл, `pgbackrest --delta restore`
отработал (сам вызов задокументирован в `patroni-pgbackrest-restore.sh` и не
менялся), но db3 **навсегда застряла** в `state=starting`:

```
2026-09-11 ... FATAL: could not receive data from WAL stream: ERROR:
  requested WAL segment 000000010000000000000006 has already been removed
2026-09-11 ... LOG: waiting for WAL to become available at 0/6000078
```

(и так — до бесконечности, раз в несколько секунд, одно и то же).

Причина: единственный full backup в репозитории (`20260910-231751F`) был снят
задолго до нескольких прошедших переключений лидера. Restore восстанавливает
базу на состояние backup (заведомо СТАРОЕ), и дальше Patroni настраивает узел
на обычную STREAMING-репликацию от текущего лидера — но `pg_wal` лидера уже
не хранит тот старый сегмент (сохранился только в архиве pgBackRest). А
`deploy/ha/patroni.yml.example` **не задавал `restore_command` вообще** — ни
для одного узла, ни как реплики, ни как потенциального будущего standby.
Значит ни один узел кластера не мог забирать недостающий WAL из архива —
только из живого `pg_wal` primary, которого к этому моменту там уже не было.

Это не специфично для guarded rebuild: **любая** реплика, отставшая от
живого `pg_wal` primary дальше, чем удерживает physical replication slot
(долгий сетевой разрыв, долгая пауза на обслуживание, да и просто эта самая
ситуация — восстановление из немного устаревшего backup), окажется в том же
тупике: постоянные неудачные попытки без единого сообщения оператору о
реальной причине, кроме голого `state=starting`/`unknown`.

**Исправлено** в `deploy/ha/patroni.yml.example`: добавлен `restore_command:
'pgbackrest --stanza=bz-get archive-get %f "%p"'` рядом с `archive_command`.
Проверено end-to-end в лаборатории: после добавления параметра в
динамический конфиг Patroni (`patronictl edit-config`) и **чистого**
перезапуска узла (важно — см. ниже) db3 сама забрала недостающие сегменты
через `archive-get`, прошла timeline-переключения 5→6→…→9→10 и вышла в
`Replica | streaming | Lag in MB: 0`; данные, вставленные во время всех
предыдущих испытаний, оказались на месте.

Практическая ловушка, обнаруженная по пути: Patroni не может применить
изменившийся `restore_command` к уже запущенному, но не принимающему
соединений узлу — сравнение текущей и желаемой конфигурации требует живого
SQL-подключения к `pg_settings`, а зависший узел его не даёт (`Failed to
determine PostgreSQL state from the connection, falling back to cached
role` → `No PostgreSQL configuration items changed, nothing to reload`).
Первый `patronictl restart db3 --force` завис на самой команде (тот же
источник проблемы — сравнение состояния перед стопом). Разрешилось только
полным `kill -9` Patroni-агента и postmaster'а узла и последующим холодным
стартом, при котором конфигурация пишется с нуля без сверки с живым
подключением. На реальном стенде это стоит знать заранее: если приёмка
столкнётся с похожим зависанием реплики, `patronictl restart` может тоже
зависнуть, и понадобится ручной перезапуск процесса.

Исправление перепроверено вторым, чистым прогоном: db1 (узел, убитый в тесте
непланового failover) поднят заново с пустого каталога данных. С уже
исправленным `restore_command` в динамическом конфиге он подключился, забрал
недостающий WAL и вышел в `Replica | streaming | Lag in MB: 0` без единого
зависания — за 15 секунд, без ручного вмешательства. Кластер вернулся к
полному составу из трёх узлов (`db1` реплика, `db2` лидер, `db3` sync
standby).

### Изолированный PITR: подтверждено, восстановление на момент времени точное

Отдельно от guarded rebuild проверен сам механизм PITR — на scratch-каталоге,
не пересекающемся с живым кластером (пятое требование раздела 8
`REBUILD_AND_DRILL.md`, «Logical corruption / PITR»).

Сценарий: вставлена строка-маркер, зафиксирован `cutoff`-timestamp,
`pg_switch_wal()` для форс-архивации, вставлена вторая строка-маркер (имитация
«порчи данных» после cutoff). Восстановление:

```
pgbackrest --stanza=bz-get --pg1-path=<scratch> \
  --type=time --target='<cutoff>+00' --target-action=promote restore
```

Результат: реплей прошёл через **пять смен timeline** (5→6→7→8→9→10 —
столько раз лидер переключался за время испытаний) без вмешательства
оператора, кроме собственно `--target`. После старта scratch-инстанса как
отдельного (не входящего в Patroni) сервера в данных ровно строка «до
cutoff» — строки «после cutoff» нет. Восстановление на момент времени точное
даже через несколько смен timeline подряд, что на практике самый частый
источник ошибок в PITR-реализациях.

### Drills Celery/Redis `kill -9`

**Redis**: `appendonly yes` / `appendfsync always` (как требует
`deploy/redis/redis-broker.conf.example`) включены вживую, запущены 20 проб с
8-секундным сном, Redis убит `kill -9` в процессе (в очереди на тот момент
оставалось 16 из 20, остальные 4 — в обработке). После рестарта Redis (без
вмешательства в воркер — Celery сам переподключился по встроенному ретраю)
очередь восстановилась из AOF полностью. Итог:
`queue_drill verify --expected-count 20` → **PASS**, все 20 завершены ровно по
одному разу, 0 потерь, 0 дублирующих бизнес-эффектов.

**Celery worker**: 20 проб с 20-секундным сном, воркер (`concurrency=4`,
`worker_prefetch_multiplier=1`, `task_acks_late=True`) убит `kill -9`
целиком (все дочерние процессы) в процессе обработки. 4 пробы застали
in-flight и остались `unacked` в Redis. `CELERY_REDIS_VISIBILITY_TIMEOUT=900`
— соответствует комментарию в `config/celery.py`: окно восстановления
рассчитано на 15 минут (дольше, чем жёсткий лимит OCR в 600 с, чтобы не
задваивать эффект на длинной задаче). Первый прогон, с ожиданием полных 900
секунд, дал **FAIL**: `completed=16, redelivered=0, never_delivered=0,
duplicate_effects=4` — ровно те же 4 пробы, что были in-flight на момент
`kill -9`, так и не завершились и не переехали обратно в очередь ни разу,
хотя воркер оставался живым и подключённым к Redis всё это время.

### Ф-8 (главная). `CELERY_REDIS_VISIBILITY_TIMEOUT` никогда не применялся — реальное окно 3600 с, а не 900

Расследование началось с прямой проверки состояния брокера: Redis-ключ
`unacked` (реестр Kombu для не подтверждённых сообщений) 20+ минут спустя
по-прежнему содержал все 4 записи с исходными timestamp'ами, а
`restore_visible()` — штатный механизм Kombu, который каждые ~10 секунд
проверяет реестр и возвращает в очередь всё, что старше
`visibility_timeout` — их не трогал. Ручной вызов `channel.qos.visibility_timeout`
на новом, чистом подключении показал **3600**, а не 900.

Причина — в самом `config/celery.py`:

```python
app.conf.broker_transport_options = {
    **(app.conf.broker_transport_options or {}),
    "visibility_timeout": redis_visibility_timeout,
}
```

Это прямое переприсваивание атрибута `app.conf.X = {...}` — **тихий no-op**
для имени, уже присутствующего в объекте, переданном в предшествующий
`config_from_object(...)` (`broker_transport_options` там есть — он задан в
Django-настройках как `{"socket_connect_timeout": 3, "socket_timeout": 3}`).
`celery.app.utils.Settings` резолвит такие имена по цепочке источников, и
слой из `config_from_object` для уже известных имён оказывается впереди
последующих прямых присваиваний. Воспроизведено минимальным скриптом без
единого импорта из проекта:

```python
app.config_from_object("django.conf:settings", namespace="CELERY")
app.conf.broker_transport_options = {"totally_new_key": "zzz"}
print(app.conf.broker_transport_options)
# {'socket_connect_timeout': 3, 'socket_timeout': 3}  — присваивание пропало
```

При этом `id()` возвращаемого словаря один и тот же при каждом чтении —
изменение **того же объекта на месте** проходит:

```python
d = app.conf.broker_transport_options
d["another"] = 1
print(app.conf.broker_transport_options)
# {'socket_connect_timeout': 3, 'socket_timeout': 3, 'another': 1}
```

Итог: собственная проверка `if redis_visibility_timeout <= 600: raise
ValueError(...)`, которая должна была не пускать в продакшен опасно короткое
значение (короче хардлимита OCR), исправно считала правильное число — но
это число никогда не попадало ни в брокер, ни куда-либо ещё. Реальным
runtime-значением всегда было встроенное значение Kombu по умолчанию — 3600
секунд, вчетверо больше документированного 15-минутного окна. Никто не
получил бы предупреждения: `app.conf.broker_transport_options`, если
смотреть на него напрямую без реального подключения, и так возвращает
верный внешний вид (словарь Django-настроек без ключа `visibility_timeout` —
то есть без противоречий, просто неполный), а drill на подставном/мокнутом
брокере (как в CI) такую тонкость вообще не видит.

**Исправлено**: `.update()` вместо переприсваивания —
`app.conf.broker_transport_options.update({"visibility_timeout":
redis_visibility_timeout})`, мутация того же объекта на месте. Проверено
через реальное подключение: `channel.qos.visibility_timeout` теперь читает
900. Добавлен регрессионный тест `apps/core/tests/test_celery_config.py`,
намеренно идущий через `app.connection_or_acquire()` и живой Redis (доступен
в CI), а не только через `app.conf` — обычная проверка `app.conf` прошла бы
даже с багом, воспроизведённым выше. Тест подтверждённо ловит откат:
временный возврат к переприсваиванию красит его в FAIL с точной
диагностикой (`'visibility_timeout' not found in {'socket_connect_timeout':
3, 'socket_timeout': 3}`).

Второй прогон worker-drill с исправлением (`lab-worker-drill-2`, тот же
сценарий: `kill -9` воркера с 4 пробами in-flight) — результат см. ниже,
после завершения повторного фонового ожидания.

## Итог

Восемь находок: семь исправлены, одна (Ф-4) вынесена на решение Заказчика.
Самая дорогая по последствиям для доверия к harness — Ф-8: документированная
и, казалось бы, проверенная кодом гарантия (15-минутное окно восстановления
Celery/Redis) на практике была фикцией — реальное окно было в 4 раза больше,
и ни один прогон drill'а на подставном брокере в CI не мог бы это заметить.
Вторая по цене для стенда — Ф-4: без неё приёмка зафиксировала бы RTO,
отличающийся от действительного в 150 раз. Третья — Ф-7: без нее guarded
rebuild реплики (единственный механизм восстановления узла, который harness
вообще умеет выполнять автоматически) навсегда зависал бы на реальном
стенде без единого диагностического сообщения о причине.

Кроме дефектов, прогон дал положительные подтверждения, тоже впервые на
живых данных: изолированный PITR восстанавливает ровно на заданный момент
через несколько смен timeline подряд; drill Redis `kill -9` с включённым AOF
проходит без потерь и дублей; drill Celery worker `kill -9` с исправленным
`visibility_timeout` — см. итог ниже, после завершения фонового ожидания.

Отдельный вывод о CI: три проверки из пяти (`amtool`, `promtool` и подставные
команды в `deploy/acceptance/validate.sh`) в CI либо пропускаются молча, либо
работают на заглушках. Ф-8 добавляет четвёртый случай того же рода: реальный
runtime-эффект конфигурации, невидимый ни в юнит-тестах (без реального
подключения к брокеру), ни в CI на моках.

Ни одна из этих находок не была видима ни в тестах приложения, ни в CI на
подставных командах. Ни одна из них не приближает Этап 4 к приёмке —
но каждая из них сэкономила бы часы стендового окна.
