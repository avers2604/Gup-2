## Политика версий: Django 5.2 LTS + Python

Официально Django 5.2 LTS поддерживает Python 3.10–3.13 (на момент выхода
релиза 3.14 ещё не существовал; официальная поддержка более новых веток
добавляется точечными релизами Django, но заранее не гарантирована). Из
этого следует прямая связка версий, а не два независимых решения:

- **Фреймворк: Django 5.2 LTS**, зафиксирован. В ветке 5.2 разрешены
  только минорные и патч-обновления (`5.2.x`); переход на следующую
  мажорную версию Django — только отдельным согласованным решением, не
  попутно с другой задачей.
- **Python: связка с Django, а не независимый выбор.**
  - `3.14.7` — candidate target (версия из исходного списка Заказчика);
  - `3.13.x` — validated fallback / текущий базовый вариант (то, на чём
    реально проверен весь код в этом репозитории);
  - итоговое решение принимается **до конца Этапа 1** по результатам
    матрицы совместимости на целевой ОС (Astra Linux / РЕД ОС / Ubuntu
    22.04+): наличие пакетов/колёс для `psycopg[binary]`, `argon2-cffi`,
    `django-storages`/`boto3`, `gunicorn` под 3.14, и подтверждение, что
    сама связка Django 5.2 + Python 3.14 protестирована (официально или
    сообществом) на момент развёртывания.
  - Правило приоритета: **если 5.2 подтверждённо стабильно работает и на
    3.14 — можно рассмотреть повышение; в обратную сторону (понижение
    Python из-за проблем с Django) решение не пересматривается — тогда
    остаёмся на 3.13.**

Если Заказчиком версия Django 6.1 зафиксирована по внешней причине
(например, уже согласована с ОС-дистрибутивом/реестром пакетов Astra
Linux или РЕД ОС и завязана на другие компоненты), это отдельный повод
вернуться к 6.1 — тогда нужно явное подтверждение, что для 6.1
обеспечена поддержка минимум на срок эксплуатации до следующего
планового обновления. Требование `condition=` вместо устаревшего
`check=` у `CheckConstraint` (совместимо и с 5.2, и с 6.1) сохранено в
коде независимо от исхода этого решения.

В этой сессии код проверен на **Django 5.2.17 + Python 3.13.12** —
именно эта связка сейчас является рабочим базовым вариантом проекта.

## Лицензии и поддержка (требуют решения Заказчика/юридической службы)

- **Redis 8.x — лицензия AGPLv3** (Redis Ltd вернула Redis на открытую
  лицензию начиная с версии 8, после периода RSAL/SSPL у 7.4). Redis
  используется здесь только как отдельный инфраструктурный сервис по
  сети (очереди Celery), не встраивается и не модифицируется в составе
  продукта — при таком использовании риски полноценных copyleft-
  обязательств обычно ниже, чем при встраивании кода, но для
  государственного заказчика в любом случае нужно формальное
  заключение юридической службы, а не техническая оценка.
  Если заключение отрицательное, план Б — **Valkey** (форк Redis под
  BSD-3, поддержан Linux Foundation, протокол-совместим с Redis).
  Valkey рассматривается как функциональная замена только после проверки
  **всей рабочей связки целиком**, не факта «клиент подключается»:
  - работа Celery через брокер (produce/consume задач конвейера OCR и
    SMTP-эскалаций из очереди на Valkey);
  - повторные попытки задач (retry/backoff Celery) ведут себя так же,
    как на Redis;
  - поведение при обрыве соединения брокер↔воркер и брокер↔Django;
  - AOF persistence и `appendfsync everysec` — те же гарантии
    долговечности очереди, что заложены для Redis;
  - `maxmemory-policy` брокера подобрана так, чтобы задачи не вытеснялись
    под памятью (для очереди задач `noeviction`, а не LRU/LFU-политики,
    рассчитанные на кеш);
  - восстановление очереди после перезапуска контейнера/процесса;
  - отсутствие дублей задач после аварийной остановки (`kill -9`) —
    прямое требование ТЗ 4.8 к DR-испытаниям очередей;
  - совместимость экспортёров и мониторинга (Prometheus-экспортёр для
    Redis должен либо работать с Valkey без изменений, либо иметь
    Valkey-эквивалент).
  Пока этот чек-лист не пройден на конкретной версии Valkey, замена не
  выполняется — это отдельная проверка перед переключением, а не
  автоматическая замена по названию/протокольной совместимости.
- **MinIO Community Edition — лицензия AGPLv3.** Решение — использовать
  community-редакцию (не коммерческую AIStor) с явным набором
  возможностей, требуемых ТЗ 4.9: Distributed mode, Erasure Coding,
  Object Locking / WORM, Versioning, контроль целостности по SHA-256
  (см. `docker-compose.yml`, `apps/core/storage.py` и поле
  `files_original_sha256` карточки НРД; разделение политик хранения —
  отдельный раздел ниже). Как и Redis, требует формального заключения
  юридической службы Заказчика о допустимости AGPLv3 в контуре
  предприятия — использование как отдельного сервиса по S3-протоколу
  (без модификации и распространения исходного кода MinIO) обычно не
  создаёт copyleft-обязательств для АИС «БЗ ГЭТ», но техническая оценка
  не заменяет юридическую.
- **ClamAV, Prometheus, Grafana, PostgreSQL, PgBouncer, etcd, nginx,
  pgBackRest, Tesseract** — постоянные открытые лицензии (GPLv2, Apache
  2.0/AGPLv3 для Grafana, PostgreSQL License, ISC/BSD и т.п.) без
  известных рисков для встраивания как инфраструктурных зависимостей;
  отдельного юридического ревью не требуют.

## Разделение политик хранения MinIO по типам объектов

**Проблема.** Единый бакет с включённым Object Locking и строгим
retention для всех объектов ломает логику ТЗ 2.2: оригиналы приказов
(`files_original`) должны быть защищены от изменения, но редактируемые
копии (`files_editable`) и файлы бланков (`Template.file_editable`,
`Template.file_sample`) правомерно заменяются — по ТЗ 4.3.1 минорная
корректировка бланка «заменяется файл бланка без прерывания жизненного
цикла». На общем бакете с WORM это технически невозможно.

**Решение — два бакета с разными политиками**, реализовано в
`apps/core/storage.py` + `config/settings/{dev,prod}.py`:

| Бакет (dev-путь) | Что хранит | Object Lock | Versioning |
|---|---|---|---|
| `originals` (`mediafiles/originals/`, prod: `MINIO_BUCKET_ORIGINALS`) | `NormativeDocument.files_original` | Да (WORM) — создаётся с `mc mb --with-lock` | включается автоматически вместе с Lock |
| `working` (`mediafiles/working/`, prod: `MINIO_BUCKET_WORKING`) | `NormativeDocument.files_editable`, `Template.file_editable`, `Template.file_sample` | Нет | включён отдельно (`mc version enable`) — история версий сохраняется, но перезапись не блокируется |

Каждое `FileField` явно указывает своё хранилище через
`storage=originals_storage` / `storage=working_storage` (callable, а не
готовый инстанс — путь к функции сохраняется в миграциях как стабильная
ссылка, инстанс хранилища не сериализуется). Бакет создаётся и
настраивается скриптом `deploy/minio/init-bucket.sh` — Object Lock можно
включить только на этапе создания бакета, задним числом нельзя.

**Локальная эмуляция vs эксплуатационная топология.** В
`docker-compose.yml` Distributed mode + Erasure Coding эмулированы на 4
локальных дисках ОДНОГО контейнера — это годится только для проверки
кода, образов и настроек бакетов, а не для реальной отказоустойчивости.
Целевая топология для эксплуатации (число узлов, число дисков на узел,
схема Erasure Coding — например N+2) в ТЗ не задана и не определена в
этом репозитории — открытый вопрос №4 ниже. При переносе в детальное
ЧТЗ (Этап 1) нужно явно развести эти два понятия, а не описывать
docker-compose-эмуляцию как целевую архитектуру.

### Открытые вопросы по хранению (требуют решения Заказчика)

1. Срок хранения архивных скан-оригиналов НРД (retention на бакете
   `originals` после перехода документа в статус «Утратил силу»/«Архив»).
2. Режим Object Locking для оригиналов — Governance (можно снять права
   admin'ом) или Compliance (нельзя снять никем до истечения срока).
3. ~~Разделение политик хранения между оригиналами, редактируемыми
   файлами и бланками~~ — реализовано (два бакета, см. выше); осталось
   решить конкретный retention/режим для `originals` (пп. 1–2).
4. Целевая топология MinIO для эксплуатации: количество узлов и дисков,
   схема Erasure Coding — сейчас в репозитории есть только
   однопроцессная dev-эмуляция, не архитектура для прода.
5. Юридическое заключение по лицензиям Redis/Valkey (AGPLv3/BSD-3) и
   MinIO Community Edition (AGPLv3) — см. «Лицензии» выше.

## Локальная разработка в этой сессии

Песочница, в которой велась разработка, не имеет доступа к пакетам
PostgreSQL 18 (в apt только 16-я ветка), к Python 3.14 (deadsnakes PPA
недоступен из контура) и к Docker Hub/Quay (нет демона Docker — образы
из `docker-compose.yml` не подтягивались и не проверялись «вживую», только
`docker compose config` на синтаксис). Проверка каркаса в этой сессии
проведена на:

- Python 3.13.12 (ближайшая доступная версия);
- PostgreSQL 16.13 (схема не использует возможностей, специфичных для
  PostgreSQL 17/18 — `tstzrange`, `EXCLUDE USING gist`, `btree_gist`
  поддерживаются начиная с PostgreSQL 9.2);
- Django 5.2.17, Gunicorn 23.0.0.

`manage.py check`, `manage.py migrate` (включая exclusion constraint по
ТЗ 4.2.3) и запуск под Gunicorn прошли чисто. Разделение хранилищ
проверено функционально: сохранённые `files_original`/`files_editable`
действительно оказываются в разных каталогах (`mediafiles/originals/` /
`mediafiles/working/`) — на локальном `FileSystemStorage`, аналог для
двух S3-бакетов в `config/settings/prod.py` не проверялся вживую (нет
доступа к MinIO/Docker в этой песочнице). Перед вводом в опытную
эксплуатацию необходимо повторить проверку на целевых версиях
PostgreSQL 18.6, подтверждённой версии Python (3.13 или 3.14.7 — см.
«Политика версий») и вживую поднятых образах
etcd/PgBouncer/ClamAV/Prometheus/Grafana/MinIO (включая сам
`init-bucket.sh` — создание бакета с `--with-lock`).
