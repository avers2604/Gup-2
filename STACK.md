## Платформа развёртывания (решение Заказчика)

Базовая ОС: **Debian 12 (Bookworm)**.

Обоснование:
- Совместимость с целевыми ОС Заказчика (**Astra Linux SE**, **РЕД ОС**
  — обе на базе Debian) — Debian 12 выбран не как самостоятельная целевая
  платформа, а как ближайшая открытая база, под которую реально собрать
  и зеркалировать пакеты для изолированного контура без прямого доступа
  к репозиториям самих Astra/РЕД ОС.
- Длительный цикл поддержки (LTS до 2033 г.).
- Простота зеркалирования репозиториев для изолированного контура (ТЗ
  предполагает контур без прямого выхода в интернет — см. «Инструменты
  зеркалирования» ниже).

Это решение сужает, а не отменяет, открытый вопрос о финальной версии
Python из раздела «Политика версий» ниже: матрица совместимости
3.13/3.14 теперь проверяется конкретно на пакетах Debian 12
Bookworm/PGDG, а не на абстрактной тройке Astra/РЕД ОС/Ubuntu.

### Стратегия установки компонентов

- **Штатные репозитории Debian 12** — etcd, ClamAV, PgBouncer,
  Tesseract 5.3.
- **Внешние официальные репозитории**:
  - PostgreSQL + Patroni + pgBackRest → `apt.postgresql.org` (PGDG);
  - nginx → `nginx.org` (stable branch);
  - Prometheus / Grafana → `packagecloud.io` / официальные репозитории
    проектов.
- **Сборка из исходников (или pre-built пакеты)**:
  - Python 3.13 (целевой baseline — см. «Политика версий»);
  - Redis 8 / Valkey (если лицензия Redis неприемлема — см. «Лицензии»
    ниже);
  - MinIO (бинарник с `dl.min.io`).
- **pip-пакеты (в виртуальном окружении)** — Django 5.2 LTS, Celery,
  Gunicorn, DRF, psycopg и др. (полный список — `requirements.txt`).

### Инструменты зеркалирования

Изолированный контур без прямого доступа в интернет — пакеты и образы
готовятся заранее на буферной машине и переносятся офлайн (ISO/каталог),
а не подтягиваются во время установки:

```bash
# На буферной машине с доступом в интернет:

# 1. Зеркало Debian 12
apt-mirror  # или aptly
# Настройка в /etc/apt/mirror.list:
# deb http://deb.debian.org/debian bookworm main contrib non-free
# deb http://security.debian.org/debian-security bookworm-security main

# 2. Зеркало PGDG (PostgreSQL)
# Подключить apt.postgresql.org, выкачать пакеты:
aptly repo create -distribution=bookworm -component=main pgdg-bookworm
aptly mirror create pgdg-bookworm https://apt.postgresql.org/pub/repos/apt bookworm-pgdg main
aptly mirror update pgdg-bookworm
aptly publish repo pgdg-bookworm

# 3. Бинарники (MinIO, Python .deb, Valkey .deb)
# Собрать и положить в отдельный каталог /opt/offline-packages/

# 4. Финальная сборка ISO-образа с зеркалом
mkisofs -o get-offline-repo.iso /opt/apt-mirror /opt/offline-packages
```

Ни зеркало, ни офлайн-сборка ISO не проверялись вживую в этой сессии
(песочница разработки без доступа к apt-mirror/aptly/mkisofs и без
самих целевых ОС) — раздел фиксирует согласованную стратегию, а не
протестированный процесс; перед реальным развёртыванием DevOps должен
пройти его целиком на буферной машине с доступом в интернет.

## Политика версий: Django 5.2 LTS + Python

Официально Django 5.2 LTS поддерживает Python 3.10–3.13 (на момент выхода
релиза 3.14 ещё не существовал; официальная поддержка более новых веток
добавляется точечными релизами Django, но заранее не гарантирована). Из
этого следует прямая связка версий, а не два независимых решения:

- **Фреймворк: Django 5.2 LTS**, зафиксирован. В ветке 5.2 разрешены
  только минорные и патч-обновления (`5.2.x`); переход на следующую
  мажорную версию Django — только отдельным согласованным решением, не
  попутно с другой задачей.
- **Python: связка с Django, а не независимый выбор.**
  - `3.14.7` — candidate target (версия из исходного списка Заказчика);
  - `3.13.x` — validated fallback / текущий базовый вариант (то, на чём
    реально проверен весь код в этом репозитории);
  - итоговое решение принимается **до конца Этапа 1** по результатам
    матрицы совместимости на платформе развёртывания (**Debian 12
    Bookworm** — см. «Платформа развёртывания» выше, решение Заказчика
    закрывает часть этого вопроса: целевая база теперь конкретная ОС, а
    не тройка кандидатов): наличие пакетов/колёс для `psycopg[binary]`,
    `argon2-cffi`, `django-storages`/`boto3`, `gunicorn` под 3.14 в
    Bookworm/PGDG-репозиториях, и подтверждение, что сама связка Django
    5.2 + Python 3.14 protестирована (официально или сообществом) на
    момент развёртывания.
  - Правило приоритета: **если 5.2 подтверждённо стабильно работает и на
    3.14 — можно рассмотреть повышение; в обратную сторону (понижение
    Python из-за проблем с Django) решение не пересматривается — тогда
    остаёмся на 3.13.**

Если Заказчиком версия Django 6.1 зафиксирована по внешней причине
(например, уже согласована с ОС-дистрибутивом/реестром пакетов Astra
Linux или РЕД ОС и завязана на другие компоненты), это отдельный повод
вернуться к 6.1 — тогда нужно явное подтверждение, что для 6.1
обеспечена поддержка минимум на срок эксплуатации до следующего
планового обновления. Требование `condition=` вместо устаревшего
`check=` у `CheckConstraint` (совместимо и с 5.2, и с 6.1) сохранено в
коде независимо от исхода этого решения.

В этой сессии код проверен на **Django 5.2.17 + Python 3.13.12** —
именно эта связка сейчас является рабочим базовым вариантом проекта.

## Лицензии и поддержка (требуют решения Заказчика/юридической службы)

- **Redis 8.x — лицензия AGPLv3** (Redis Ltd вернула Redis на открытую
  лицензию начиная с версии 8, после периода RSAL/SSPL у 7.4). Redis
  используется здесь только как отдельный инфраструктурный сервис по
  сети (очереди Celery), не встраивается и не модифицируется в составе
  продукта — при таком использовании риски полноценных copyleft-
  обязательств обычно ниже, чем при встраивании кода, но для
  государственного заказчика в любом случае нужно формальное
  заключение юридической службы, а не техническая оценка.
  Если заключение отрицательное, план Б — **Valkey** (форк Redis под
  BSD-3, поддержан Linux Foundation, протокол-совместим с Redis).
  Valkey рассматривается как функциональная замена только после проверки
  **всей рабочей связки целиком**, не факта «клиент подключается»:
  - работа Celery через брокер (produce/consume задач конвейера OCR и
    SMTP-эскалаций из очереди на Valkey);
  - повторные попытки задач (retry/backoff Celery) ведут себя так же,
    как на Redis;
  - поведение при обрыве соединения брокер↔воркер и брокер↔Django;
  - AOF persistence и `appendfsync everysec` — те же гарантии
    долговечности очереди, что заложены для Redis;
  - `maxmemory-policy` брокера подобрана так, чтобы задачи не вытеснялись
    под памятью (для очереди задач `noeviction`, а не LRU/LFU-политики,
    рассчитанные на кеш);
  - восстановление очереди после перезапуска контейнера/процесса;
  - отсутствие дублей задач после аварийной остановки (`kill -9`) —
    прямое требование ТЗ 4.8 к DR-испытаниям очередей;
  - совместимость экспортёров и мониторинга (Prometheus-экспортёр для
    Redis должен либо работать с Valkey без изменений, либо иметь
    Valkey-эквивалент).
  Пока этот чек-лист не пройден на конкретной версии Valkey, замена не
  выполняется — это отдельная проверка перед переключением, а не
  автоматическая замена по названию/протокольной совместимости.
- **MinIO Community Edition — лицензия AGPLv3.** Решение — использовать
  community-редакцию (не коммерческую AIStor) с явным набором
  возможностей, требуемых ТЗ 4.9: Distributed mode, Erasure Coding,
  Object Locking / WORM, Versioning, контроль целостности по SHA-256
  (см. `docker-compose.yml`, `apps/core/storage.py` и поле
  `files_original_sha256` карточки НРД; разделение политик хранения —
  отдельный раздел ниже). Как и Redis, требует формального заключения
  юридической службы Заказчика о допустимости AGPLv3 в контуре
  предприятия — использование как отдельного сервиса по S3-протоколу
  (без модификации и распространения исходного кода MinIO) обычно не
  создаёт copyleft-обязательств для АИС «БЗ ГЭТ», но техническая оценка
  не заменяет юридическую.
- **ClamAV, Prometheus, Grafana, PostgreSQL, PgBouncer, etcd, nginx,
  pgBackRest, Tesseract** — постоянные открытые лицензии (GPLv2, Apache
  2.0/AGPLv3 для Grafana, PostgreSQL License, ISC/BSD и т.п.) без
  известных рисков для встраивания как инфраструктурных зависимостей;
  отдельного юридического ревью не требуют.

## Разделение политик хранения MinIO по типам объектов

**Проблема.** Единый бакет с включённым Object Locking и строгим
retention для всех объектов ломает логику ТЗ 2.2: оригиналы приказов
(`files_original`) должны быть защищены от изменения, но редактируемые
копии (`files_editable`) и файлы бланков (`Template.file_editable`,
`Template.file_sample`) правомерно заменяются — по ТЗ 4.3.1 минорная
корректировка бланка «заменяется файл бланка без прерывания жизненного
цикла». На общем бакете с WORM это технически невозможно.

**Решение — два бакета с разными политиками**, реализовано в
`apps/core/storage.py` + `config/settings/{dev,prod}.py`:

| Бакет (dev-путь) | Что хранит | Object Lock | Versioning |
|---|---|---|---|
| `originals` (`mediafiles/originals/`, prod: `MINIO_BUCKET_ORIGINALS`) | `NormativeDocument.files_original`, `Template.file_editable`, `Template.file_sample` | Да (WORM) — создаётся с `mc mb --with-lock` | включается автоматически вместе с Lock |
| `working` (`mediafiles/working/`, prod: `MINIO_BUCKET_WORKING`) | `NormativeDocument.files_editable` | Нет | включён отдельно (`mc version enable`) — история версий сохраняется, но перезапись не блокируется |

`Template.file_editable`/`file_sample` переехали из `working` в `originals`
по итогам ревью — см. разбор «двухступенчатой модели» ниже (закрывает
открытый вопрос №4).

Каждое `FileField` явно указывает своё хранилище через
`storage=originals_storage` / `storage=working_storage` (callable, а не
готовый инстанс — путь к функции сохраняется в миграциях как стабильная
ссылка, инстанс хранилища не сериализуется). Бакет создаётся и
настраивается скриптом `deploy/minio/init-bucket.sh` — Object Lock можно
включить только на этапе создания бакета, задним числом нельзя.

**Локальная эмуляция vs эксплуатационная топология.** В
`docker-compose.yml` Distributed mode + Erasure Coding эмулированы на 4
локальных дисках ОДНОГО контейнера — это годится только для проверки
кода, образов и настроек бакетов, а не для реальной отказоустойчивости.
Целевая топология для эксплуатации (число узлов, число дисков на узел,
схема Erasure Coding — например N+2) в ТЗ не задана и не определена в
этом репозитории — открытый вопрос №3 ниже. При переносе в детальное
ЧТЗ (Этап 1) нужно явно развести эти два понятия, а не описывать
docker-compose-эмуляцию как целевую архитектуру.

### Матрица сроков хранения и режимов WORM по категориям (закрывает вопросы №1-2)

Заказчик прислал детальную матрицу — retention не одинаковый для всего
бакета `originals`, он зависит от юридической категории документа.
Реализовано в `apps/documents/retention.py` (данные + резолвер) и полях
`NormativeDocument.retention_category/retention_mode/retention_until`
(категория — обязательное поле, выбирается человеком при регистрации;
режим и срок считаются автоматически из категории в `save()`):

| Категория | Типичный срок | Режим | Основание |
|---|---|---|---|
| Приказы по основной деятельности | Постоянно | Compliance | Перечень Росархива, ст. 22.1 ФЗ-125 |
| Приказы по личному составу | 50 лет (75 — если до 2003 г.) | Compliance | Ст. 22.1 ФЗ-125 |
| Распоряжения оперативного характера | 5 лет ЭПК | Governance | Перечень Росархива |
| Акты расследований ДТП, сходов, Н-1 | 45 / 75 лет | Compliance | ФЗ-125, Ространснадзор |
| Наряды-допуски, протоколы испытаний ЭХ | 10 лет | Governance | ПТЭ, Ростехнадзор |
| Бланки и типовые формы (утверждённые) | Постоянно | Governance | Внутренний регламент ГЭТ |
| Архивные сканы (до 2017 г.) | Постоянно | Compliance | Исторический фонд |
| Документы ДСП | До рассекречивания + 30 лет | Compliance | ФЗ-149, внутренний ЛНА о ДСП |

Из восьми категорий к карточке НРД сейчас применимы пять (приказы по
основной деятельности/личному составу, оперативные распоряжения,
архивные сканы, ДСП) — `NORMATIVE_DOCUMENT_CATEGORIES` в
`retention.py`, `clean()` отклоняет остальные три с понятной ошибкой.
Оставшиеся две категории не отброшены, а сознательно заведены как
данные на будущее:

- **«Акты расследований ДТП/Н-1» и «Наряды-допуски, протоколы
  испытаний ЭХ»** — это не НРД, а заполняемые через будущий «Мастер
  заполнения» акты (ТЗ 4.3.2, Этап 2). Модели для них ещё нет; когда
  появится, она заберёт готовые категории из той же матрицы.
- **«Бланки и типовые формы (утверждённые)» — Governance, «постоянно».
  Закрыто двухступенчатой моделью (решение по итогам ревью, закрывает
  открытый вопрос №4).** Изначально здесь виделось архитектурное
  противоречие: матрица требует Governance-лока на утверждённые бланки
  как на «эталоны», а более раннее решение держало
  `Template.file_editable`/`file_sample` в НЕзаблокированном `working`,
  чтобы минорная корректировка (ТЗ 4.3.1) могла заменить файл без
  прерывания жизненного цикла записи. Ключевое наблюдение при повторном
  чтении ТЗ 4.3.1: версия бланка инкрементируется ДАЖЕ для минорной
  корректировки (v1.0 → v1.1) — то есть каждая строка `Template` с самого
  начала является уже ОПУБЛИКОВАННЫМ, неизменяемым артефактом, а не
  черновиком, который правится на месте. Противоречия не было — было
  неверное предположение, что «минорная корректировка» означает мутацию
  существующего файла.

  Принята **двухступенчатая модель**:
  1. `Template.file_editable`/`file_sample` теперь лежат в заблокированном
     `originals` (Governance, `TEMPLATES_APPROVED` из
     `RETENTION_MATRIX`, `retention.py`) — каждая строка = опубликованная,
     неизменяемая версия.
  2. Незаблокированная рабочая копия для правки ДО публикации новой
     версии — отдельный, пока НЕ реализованный механизм черновиков
     (будущий Этап 2/3 UI, «Мастер публикации бланка»): Контролёр/Юрист
     (роль, унаследовавшая функционал упразднённого «Куратора службы» —
     см. «Упразднение роли «Куратор службы»» ниже) правит
     черновик в неблокированном пространстве, а «публикация» создаёт
     НОВУЮ строку `Template` с новым `version` и пишет файлы уже в
     `originals`. Governance (в отличие от Compliance) всё равно
     оставлен как режим — не потому что файл планируется перезаписывать
     на месте, а чтобы явно ошибочно опубликованную версию можно было
     снять с блокировки привилегированной операцией
     (`x-amz-bypass-governance-retention` + `s3:BypassGovernanceRetention`),
     а не жить с ней вечно как с Compliance-объектом.

  `Template.RETENTION_MODE` (константа класса, всегда `GOVERNANCE`) и
  сама привязка к `originals_storage` реализованы; механизм черновиков —
  нет, это отдельная будущая задача, отмечена явно, а не смешана с уже
  сделанным.

**Честная граница текущей реализации.** `retention_mode`/`retention_until`
сейчас — это поля в Postgres (видны в админке, пригодны для отчётности
и мониторинга по ТЗ 4.8), но они ещё НЕ прокинуты в реальные S3-заголовки
MinIO (`x-amz-object-lock-mode`, `x-amz-object-lock-retain-until-date`)
при загрузке файла — `get_object_parameters()` в django-storages получает
на вход только имя файла, не объект модели, поэтому per-объектный Lock с
датой, разной для каждого документа, требует отдельного connecting layer
(например, contextvar, который `NormativeDocument.save()` выставляет
перед сохранением FileField, и который читает переопределённый storage-
класс). Это Этап 3/4: реализовать и проверить можно только на живом
MinIO, которого в этой песочнице нет — тут дал бы untested код с
ложным чувством, что WORM для оригиналов уже действует на уровне
хранилища. Пока фактическая защита оригиналов от изменения — то, что
уже реально работает: WORM-журнал аудита (DB-триггер) и то, что бакет
`originals` в принципе создаётся с `--with-lock` (см. `init-bucket.sh`).

### Доработки retention по итогам второго ревью

Все — в `apps/documents/retention.py` и `NormativeDocument.save()`,
тесты — `apps/documents/tests/test_retention.py`.

- **`is_retention_still_binding(retention_until, as_of=None)`.**
  `retention_until=None` означает ОДНО из двух: «постоянно» ИЛИ «срок ещё
  не может быть посчитан» (ДСП без даты рассекречивания) — в обоих
  случаях блокировка ещё действует. Голая проверка вида
  `if retention_until and retention_until < today` трактует `NULL` как
  falsy и тем самым как «ограничений нет» — ровно обратное задуманному.
  Эта функция — единственное место, где `retention_until` полагается
  сравнивать с датой; весь будущий код (в том числе будущая интеграция с
  MinIO) должен звать её, а не писать сравнение напрямую.
- **Заморозка `retention_until`.** Раньше `NormativeDocument.save()`
  пересчитывал `retention_mode`/`retention_until` на КАЖДОЕ сохранение —
  при простом пересохранении карточки (например, после правки `title`)
  дата могла «уехать», если к тому моменту изменилось что-то ещё,
  влияющее на резолвер. Теперь пересчёт — только при первом сохранении
  или при фактической смене `retention_category` (сравнение с БД-версией
  до `save()`, тот же приём, что и `User.save()`/`was_blocked`).
- **Аудит смены категории.** Смена `retention_category` ПОСЛЕ создания
  карточки — изменение юридической классификации, а не техническая
  правка, и обязана попасть в WORM-журнал: новый тип события
  `AuditLog.EventType.DOCUMENT_RETENTION_CATEGORY_CHANGED` со старым и
  новым значением в `details`. Первое присвоение категории при создании
  документа НЕ считается «сменой» (это классификация с нуля) и не
  логируется этим событием.
- **`is_expired_at_intake(retention_until, as_of=None)` +
  предупреждение в аудите.** Обратная загрузка старого документа с
  коротким сроком хранения может дать `retention_until` уже в прошлом на
  момент регистрации (типичный случай для `ARCHIVAL_SCANS`) — это не
  ошибка данных, но и не то, что должно пройти незамеченным. При первом
  сохранении с уже просроченным вычисленным сроком пишется
  информационная запись `AuditLog.EventType.DOCUMENT_RETENTION_EXPIRED_AT_INTAKE`
  — решение, что с этим делать (снимать блокировку сразу, оставлять
  документ вообще), остаётся за Контролёром/Юристом, автоматика его не
  принимает.
- **`is_active`/`stage` в `RetentionPolicy`.** `ACTS_INVESTIGATION` и
  `PERMITS_EH` заведены в `RETENTION_MATRIX` как данные (матрица
  присылалась Заказчиком целиком), но ни одна модель их ещё не
  использует — помечены `is_active=False, stage="Этап 2 (Мастер
  заполнения актов)"`, чтобы будущий UI/API явно проверял этот флаг и не
  предлагал их к выбору раньше времени.
- **`object_lock_params_for(policy, retention_until)`.** Чистая функция,
  переводящая политику + вычисленную дату в точные параметры S3 Object
  Lock (`ObjectLockMode`, `ObjectLockLegalHoldStatus`,
  `ObjectLockRetainUntilDate`) — готова для вызова из будущего
  MinIO-клиента, но сама никуда пока не подключена (клиента, реально
  загружающего файлы в MinIO, в проекте ещё нет). Для `retention_until=None`
  (постоянное/неопределённое хранение) сознательно возвращает
  `legal-hold=ON`, а не `retain-until-date` с произвольно далёкой датой —
  «далёкая дата» это подделка постоянства, создающая риск, что в будущем
  кто-то ошибочно решит, что срок истёк естественным образом.

### Чек-лист интеграции с живым MinIO (Этап 3/4, нужен реальный MinIO)

Ничего из этого нельзя ни реализовать по-настоящему, ни проверить без
живого MinIO — здесь фиксируется, ЧТО именно предстоит сделать, чтобы не
потерять контекст между сессиями:

1. При загрузке файла передавать `x-amz-object-lock-mode`,
   `x-amz-object-lock-retain-until-date`, `x-amz-object-lock-legal-hold` —
   значения берутся из `object_lock_params_for()` (уже готова, см. выше).
2. Бакет `originals` обязан быть создан с `ObjectLockEnabled=true`
   (`mc mb --with-lock`, уже в `init-bucket.sh`) — это настраивается
   ТОЛЬКО при создании бакета, задним числом невозможно.
3. Перед загрузкой проверять `is_expired_at_intake()`/
   `is_retention_still_binding()` и явно решать по политике: блокировать
   загрузку с уже истёкшим сроком или разрешать её без Object Lock —
   сейчас это решение не принято за Заказчика (см. предупреждение в
   аудите выше, которое лишь сигнализирует о ситуации, не блокирует её).
4. Для категорий с `retention_until=None` — `legal-hold: ON`, не
   `retain-until-date` (см. `object_lock_params_for`).
5. Тестовые сценарии на живом MinIO: (а) удаление ДО истечения срока —
   должно падать и для Governance, и для Compliance; (б) удаление ПОСЛЕ
   истечения — успешно для обоих режимов; (в) привилегированный
   bypass Governance ДО истечения срока — должен успешно проходить и
   обязан писать событие в WORM-журнал аудита (кто, когда, для какого
   объекта, с каким обоснованием).
6. **Вопросы, требующие явного решения Заказчика/ЧТЗ (не решаются
   автоматикой):** кто именно имеет право на
   `bypass-governance-retention` — только Офицер ИБ, или Офицер ИБ +
   Контролёр/Юрист вдвоём (принцип двух пар глаз для юридически значимой
   операции)? При каких условиях блокировка вообще может быть снята
   досрочно (человеческая ошибка при публикации, судебный запрос,
   что-то ещё)? Как сама операция снятия аудируется — отдельный тип
   события, обязательное текстовое обоснование?

### Разделение ролей БД для WORM-журнала — чек-лист Этапа 3 (ЧТЗ)

Триггеры (BEFORE UPDATE/DELETE/TRUNCATE) — реальная защита уже сейчас, но
её предел честно обозначен выше: роль-владелец таблицы технически может
их отключить. Полная защита требует разделения ролей на уровне
эксплуатации, не Django-миграции — это должно попасть в ЧТЗ/план работ
Этапа 3 как явное требование:

1. Владелец таблицы `audit_auditlog` (и её триггеров/функции) — отдельная
   служебная роль БД, от имени которой применяются миграции; НЕ совпадает
   с ролью, от имени которой подключается работающее приложение.
2. Прикладная роль (та, что в `POSTGRES_USER`/`DATABASE_*` у Django) имеет
   на `audit_auditlog` только `INSERT` и `SELECT`. Явно нет `UPDATE`,
   `DELETE`, нет прав на `ALTER TABLE` (в том числе на отключение/удаление
   триггеров — это следует из отсутствия ownership, а не отдельный GRANT).
3. Прикладной роли явно запрещён `TRUNCATE` (`REVOKE TRUNCATE ON
   audit_auditlog FROM <app_role>`) — отдельно от триггера (4), это
   защита в глубину: даже если кто-то отключит триггер, роль всё равно
   технически не сможет выполнить TRUNCATE без грантов.

Пока это не сделано (Этап 3), фактическая защита — только триггерная
(п. 3 в таблице выше), с её честно описанным пределом.

**Проверено по итогам ревью — `TRUNCATE ... CASCADE` через FK не обходит
триггер.** Три конкретных пункта:

1. Триггер `audit_auditlog_worm_guard_truncate` — `BEFORE TRUNCATE` (не
   `AFTER`), проверка числа строк выполняется в той же транзакции, что и
   сам TRUNCATE — отменить операцию (`RAISE EXCEPTION`) можно только на
   `BEFORE`, `AFTER` было бы уже поздно.
2. `TRUNCATE ... CASCADE` затрагивает `audit_auditlog` только если на неё
   ссылается FK с `ON DELETE CASCADE` из другой таблицы, которую
   truncate'ят. Проверено (`grep -rn "ForeignKey(.*AuditLog"` по `apps/`,
   пусто) — ни одна модель не хранит FK на `AuditLog`: у неё нет полей,
   которые логично было бы связывать внешним ключом (только
   `actor` → `User`, в обратную сторону), так что `TRUNCATE ... CASCADE`
   какой-либо другой таблицы органически не может дотянуться до журнала
   аудита. `RESTRICT` явно объявлять не потребовалось — ссылок физически
   нет, а не запрещены отдельным правилом.
3. Альтернатива (не выбрана, но зафиксирована для полноты) — пометить
   `AuditLog` так, чтобы `TransactionTestCase` не пытался её `TRUNCATE`
   между тестами, и гонять её тесты через обычный `TestCase`. Текущее
   решение (условный триггер «пусто — можно, не пусто — нельзя», см.
   `audit.0005_worm_truncate_trigger`) не требует менять тестовую
   инфраструктуру и защищает не только тесты, но и любой `TRUNCATE` в
   проде — оставлено основным.

### Открытый вопрос: линейный порядок привилегий ролей (ТЗ 4.6)

`User.ROLE_PRIVILEGE_ORDER` (apps/iam/models.py) — линейный список,
изначально дословно повторявший порядок перечисления ролей в самом ТЗ 4.6:
Читатель < Куратор < Контролёр/Юрист < Офицер ИБ < Администратор. С этой
сессии — Читатель < Методист подразделения < Контролёр/Юрист < Офицер ИБ
< Администратор (роль «Куратор» упразднена, «Методист подразделения»
добавлена — см. «Упразднение роли «Куратор службы»» ниже). Используется
для определения «повышения роли» при импорте персонала
(апп.iam.services._is_role_elevated) — переход в audit-событие
`user.role_elevated`.

Формально это допустимо (порядок взят из самого ТЗ, не придуман), но
содержательно **Офицер ИБ и Контролёр/Юрист — параллельные ветки
аудита** (безопасность vs юридическая проверка), а не одна выше другой.
Линейная модель делает переходы между ними асимметричными: Контролёр →
Офицер ИБ сейчас засчитывается как «повышение» (индекс 3 > индекс 2) и
пишется в WORM-аудит, а Офицер ИБ → Контролёр — как понижение и НЕ
пишется, хотя по смыслу это скорее два равнозначных случая
«перевод между специализированными ролями», которые либо оба должны
аудироваться, либо ни один.

Не решено самостоятельно — нужно зафиксировать в ЧТЗ или протоколе
согласования с Заказчиком: считать ли любой переход между
`controller_lawyer` и `security_officer` (в любую сторону) поводом для
audit-записи, и если да — добавить отдельную проверку в
`_is_role_elevated()` (не полагаясь только на линейный индекс) до того,
как через импорт реально пройдёт такой переход.

### Усиление аудита (решение Заказчика)

Четыре независимых расширения WORM-журнала, все — `apps/audit/models.py`
→ новые `AuditLog.EventType` + код, который их пишет:

1. **Изменения ролей пользователей.** Новое событие `USER_ROLE_CHANGED`
   пишется из `User.save()` при ЛЮБОМ фактическом изменении `role`
   (сравнение с БД тем же паттерном, что и `was_blocked`/
   `retention_category` — см. их докстринги) — независимо от направления
   (не только повышение) и независимо от HTTP-контура или его отсутствия
   (admin, `import_personnel`, любой будущий код). Оператор передаётся
   через транзитный атрибут `_audit_actor` (не поле модели — не должен
   персистироваться), который обязан выставить вызывающий код ДО
   `save()` (`UserAdmin.save_model`, `import_personnel`), потому что у
   `save()` самого по себе нет доступа к HTTP-запросу.
   **Намеренное пересечение с `USER_ROLE_ELEVATED`:** более узкое
   существовавшее событие (только повышение, только импорт персонала,
   `apps.iam.services._is_role_elevated`) НЕ убрано и НЕ заменено —
   оба события могут быть записаны на одно и то же изменение роли при
   импорте. Это две разные вещи под разных потребителей: узкий сигнал
   «повышение конкретно при импорте» (уже был, есть тесты) и комплексный
   «любое изменение роли отовсюду» (новое требование). Не объединены в
   одно, чтобы не переписывать семантику уже протестированного узкого
   события ради нового требования.
2. **Входы и выходы.** `record_session_login`/`record_session_logout`
   (`apps/iam/services.py`) теперь пишут в `details` снимок ФИО, роли и
   IP-адреса — раньше был только табельный номер
   (`actor_personnel_number`) и метка времени (`created_at`). IP —
   `request.META["REMOTE_ADDR"]` напрямую, **честная граница**: без учёта
   заголовков reverse-proxy (`X-Forwarded-For`/`X-Real-IP`). За
   балансировщиком/nginx `REMOTE_ADDR` будет адресом самого прокси, не
   клиента; доверенная обработка таких заголовков (с явным списком
   доверенных прокси — иначе клиент подделывает IP, просто отправив свой
   `X-Forwarded-For`) специфична для целевой топологии развёртывания,
   которой в этой сессии нет (см. «Локальная разработка в этой сессии»)
   — отложено до Этапа 3/4, не реализовано вслепую.
   Новое событие `SESSION_LOGIN_FAILED` — неудачные попытки входа, пишется
   из `check_credentials()` (неверный пароль/табельный номер/
   заблокированный пользователь — одно сообщение на все три случая, как и
   раньше, но теперь ещё и общее событие аудита) и из `verify_totp_login()`
   (невалидный/просроченный тикет, пользователь заблокирован между шагами,
   неверный код TOTP) — основа Grafana-алерта «5+ попыток подряд» (см. ниже).
   Работает одинаково в обоих контурах (Web и API), потому что вызывается
   из общего `apps/iam/services.py`, а не задублировано в `views.py`/`api.py`.
3. **Изменения документов и бланков.** `NormativeDocument.save()`
   расширен тем же паттерном, что уже использовался для
   `retention_category`: сравнение `status` с БД до `super().save()`.
   Новое событие `DOCUMENT_STATUS_CHANGED` — универсальный случай; для
   двух самых однозначных переходов используются уже существовавшие, но
   ни разу не писавшиеся события `DOCUMENT_PUBLISHED` (→ `ACTIVE`) и
   `DOCUMENT_REVOKED` (→ `REVOKED`) — самостоятельное решение
   картографии «новый статус → тип события», не единственно возможное,
   задокументировано в докстрайне `save()`. `Template` получил свой
   ПЕРВЫЙ `save()` (раньше его не было вовсе) с тем же паттерном:
   `ACTIVE → SUPERSEDED` пишет `TEMPLATE_SUPERSEDED` (тоже существовавшее,
   ни разу не писавшееся событие); любой другой переход — `TEMPLATE_UPDATED`
   как честная заготовка (`TemplateAdmin.save_model` сейчас блокирует
   любое изменение уже опубликованной версии через админку, так что этой
   веткой пока некому воспользоваться, кроме будущего механизма
   отката/черновиков). Оператор — тот же `_audit_actor`, выставляется в
   `NormativeDocumentAdmin.save_model`/`TemplateAdmin.save_model`.
4. **Grafana-алерты** — новый `deploy/grafana/provisioning/` (датасорс
   `postgres.yml` + правила `alerting/audit-alerts.yml`), файловый
   provisioning Grafana unified alerting напрямую поверх `audit_auditlog`
   (native SQL-алертинг, без отдельного пайплайна метрик/экспортёров —
   WORM-журнал уже единственный источник истины для всех пяти условий).
   `docker-compose.yml` → сервис `grafana` получил монтирование
   `./deploy/grafana/provisioning` и переменные `POSTGRES_*` для
   подстановки в датасорс. Пять условий:
   - **5+ неудачных попыток подряд** — `SESSION_LOGIN_FAILED`,
     группировка по `actor_personnel_number`, окно 15 минут, `HAVING
     COUNT(*) >= 5`. Полностью работоспособно (событие реально пишется, см. п.2).
   - **Вход с необычного IP** — эвристика: IP успешного `SESSION_LOGIN`,
     не встречавшийся у этого табельного номера за предыдущие 30 дней
     (`NOT EXISTS` по истории того же `event_type`). Не полноценная
     модель поведения (гео-IP/устройство/ASN не подключены) — честная
     эвристика по отсутствию точного совпадения, задокументирована как
     таковая в самом YAML. Работоспособно, т.к. `ip_address` теперь
     реально попадает в `details` (см. п.2).
   - **Массовое скачивание ДСП (>5/час)** — ссылается на
     `EXPORT_RESTRICTED` (`event.type` заведён ещё на Этапе 1). **Честная
     граница: в проекте нет ни одной вьюхи скачивания документов ДСП ни в
     одном контуре** — правило сконфигурировано (условие «настроить
     алерт» выполнено буквально) и сработает автоматически, когда
     появится реальный источник события, но физически не может сработать
     сейчас. Промаркировано `status: dormant-no-producer-yet` в самом YAML.
   - **Смена статуса документа в нерабочее время** — использует новые
     `DOCUMENT_PUBLISHED`/`DOCUMENT_REVOKED`/`DOCUMENT_STATUS_CHANGED`
     (п.3). «Рабочее время» принято как Пн–Пт 08:00–20:00 (Europe/Moscow)
     — ТЗ конкретных часов не задаёт, это самостоятельное допущение, не
     вычитанное из документа буквально. Работоспособно.
   - **Экспорт журнала аудита** — новое событие `AUDIT_LOG_EXPORTED`,
     такая же заготовка, как «Массовое скачивание ДСП»: в проекте нет
     функции экспорта самого журнала аудита ни в одном контуре. Правило
     готово, событие пока не пишется, промаркировано аналогично.
   Ни разу не проверено вживую (нет доступа к Docker-демону в этой
   песочнице — см. «Локальная разработка в этой сессии» ниже), только на
   соответствие документированной схеме provisioning YAML Grafana ≥9.1.
   `contactPoints`/`policies` в `audit-alerts.yml` — плейсхолдер
   (условный email-адрес), реальный канал уведомлений Заказчиком не выбран.

### 2FA только для Администратора (решение Заказчика, сужение)

`User.requires_totp` (apps/iam/models.py) было
`{ADMINISTRATOR, CONTROLLER_LAWYER, CURATOR}`, стало — только
`ADMINISTRATOR`. С упразднением `CURATOR` и сужением 2FA одновременно
`CONTROLLER_LAWYER` тоже выпал из обязательных — эти два изменения не
независимы: если бы 2FA не сузили, унаследовавший функционал куратора
`CONTROLLER_LAWYER` продолжил бы требовать 2FA просто по факту того, что
уже требовал его до этой сессии. Явного вопроса от Заказчика на этот счёт
не поступало отдельно от прямой формулировки «2ФА остаётся только для
роли «Администратор»» — трактовано буквально, без дополнительных исключений.

### Парольная политика (решение Заказчика)

`config/settings/base.py` → `AUTH_PASSWORD_VALIDATORS`:

- **Минимальная длина — 14** (`MinimumLengthValidator`, было 10).
- **Проверка по чёрному списку** — принят встроенный
  `CommonPasswordValidator` Django (словарь ~20000 самых частых
  скомпрометированных паролей). Заказчик не присылал отдельный
  корпоративный словарь (в отличие, например, от тезауруса Smart Search,
  где файл был прислан явно) — собственный список не придуман
  самостоятельно, использован стандартный инструмент Django для той же цели.
- **История 10 паролей** — новая модель `PasswordHistoryEntry`
  (`apps/iam/models.py`, хэш пароля + `user` FK + `created_at`), новый
  `apps.iam.validators.PasswordHistoryValidator`. Наполнение истории —
  внутри `User.save()`, тем же паттерном "сравнить с БД до
  `super().save()`": на реальном изменении хэша пароля (не на создании
  записи — не с чем сравнивать) в историю попадает именно ЗАМЕНЯЕМЫЙ
  (старый) хэш, после чего хранится только последние
  `PASSWORD_HISTORY_DEPTH=10` записей на пользователя (более старые
  удаляются). Валидатор без `user`/у нового несохранённого `User` —
  пропускает проверку (истории физически неоткуда взяться), это не
  нарушение политики, а её область применения.
  Валидаторы Django запускаются автоматически там, где уже вызывается
  `password_validation.validate_password()` — формы admin
  (`UserCreationForm`/`AdminPasswordChangeForm`) и `createsuperuser`;
  отдельной вьюхи смены пароля в проекте ещё нет ни в одном контуре
  (тот же честный пробел, что и `password_change_required` ниже).
- **Срок действия — 365 дней.** Новое поле `User.password_changed_at`
  (выставляется в `save()` при любой реальной смене хэша пароля,
  включая первую установку при создании учётной записи) + свойство
  `User.is_password_expired`. **ТОЛЬКО информационный флаг** — той же
  честной границы, что и `status=PASSWORD_CHANGE_REQUIRED` (см. раздел
  про 2FA/логин ниже): ни один Web/API эндпоинт его не проверяет и не
  блокирует вход, потому что в проекте нет ни одной вьюхи смены пароля,
  на которую можно было бы принудительно перенаправить. `password_changed_at
  = NULL` (учётная запись без отслеживаемой истории) трактуется как «не
  просрочен», а не наоборот — в отличие от `retention_until`, здесь
  ложное «не просрочен» не угроза безопасности сама по себе, только
  повод администратору поднять историю вручную.

### Таймаут неактивности: 30/15 минут (решение Заказчика)

`settings.SESSION_COOKIE_AGE` — было 15 минут безусловно, стало 30 минут
по умолчанию (личное рабочее место). `LoginForm` (`apps/iam/forms.py`)
получила чекбокс `shared_terminal` («Это компьютер общего доступа
(терминал)») — если отмечен, `apps/iam/views.py` вызывает
`request.session.set_expiry(15 * 60)` в момент завершения входа (оба
случая — прямой вход без 2FA и завершение после `TotpVerifyView`, значение
чекбокса донесено через pending-сессию между шагами). Без отметки —
`set_expiry(None)`, что явно означает «вернуться к глобальному умолчанию»
(30 минут), а не хардкод того же числа на другом уровне.

**Специфично для Web GUI по архитектуре, не по недосмотру:** различие
«личное рабочее место / терминал общего доступа» осмысленно только для
браузерной сессии сотрудника на конкретном устройстве. В External
API/JWT-контуре нет понятия «рабочее место» — там свой отдельный таймаут,
`ACCESS_TOKEN_LIFETIME` (`SIMPLE_JWT`, 15 минут, не менялся в этой
партии) — никак не связан с `SESSION_COOKIE_AGE` и не должен был
меняться вместе с ним.

### Решено: сброс сессий только при блокировке, не при смене роли (ТЗ 4.7)

`User.save()` (apps/iam/models.py) вызывает `force_logout_user()` только
на переход `status -> BLOCKED`. Более ранние редакции ТЗ (2.0/2.1)
формулировали это как «принудительный сброс сессий сотрудника при смене
его роли ИЛИ блокировке аккаунта» — в присланной ревизии 2.2 формулировка
сжалась до «при блокировке пользователя».

**Подтверждено Заказчиком:** сужение в 2.2 — намеренное, не потерянная
при переписывании формулировка. Реализация уже соответствует 2.2
дословно и изменений не требует. Смена роли сама по себе сброс сессий
не вызывает.

## apps/search_ocr — тезаурус Smart Search (ТЗ 4.4.1)

Пользователь прислал `docs/thesaurus/thesaurus_v0.9_draft.json` (217
записей: аббревиатуры/синонимы отраслевой терминологии ГЭТ, статус
`0.9.0-draft`, на момент присылки явно требовал верификации кураторами
служб — роль с тех пор упразднена, см. «Упразднение роли «Куратор
службы»» выше; сам файл как исходные данные намеренно не редактировался
задним числом под новую роль, это снимок присланного материала) — закрывает
открытый вопрос №4 исходного плана (лингвистический модуль Smart
Search). Файл необычен тем, что сам специфицирует и данные, и контракт
их проверки: `meta.schema`, `validation_rules` (коды TH-01..TH-08),
`loading_notes` (стратегия upsert по id, событие аудита
`THESAURUS_UPDATED`). Реализация следует этому контракту, а не
придумывает свой — подробности того, какое TH-правило проверяется на
уровне модели `ThesaurusEntry`, какое — в `import_thesaurus()`
(apps/search_ocr/services.py) и как файловые правила (TH-02/03/08)
сообщаются предупреждением, а не отказом, см. docstring'и в
`apps/search_ocr/models.py` и `services.py`.

**Два исправления в самом файле** (сделаны на этой сессии, не тихо, а
с явной фиксацией здесь — это правки синтаксиса/опечаток, а не
содержательные решения, требующие Заказчика):
1. `services.null` был невалидным JSON (голый `null` как ключ объекта
   вместо `"null"` в кавычках) — файл не парсился вообще. Поправлено на
   строковый ключ `"null"` без изменения смысла (ровно то же
   назначение: «общепредприятийский термин»).
2. Два id (`snegoуборочный_vagon`, `стык_relsov`) содержали смешение
   кириллицы и латиницы — опечатка, ломающая `SlugField`. Переименованы
   в `snegouborochnyy_vagon`/`styk_relsov` по образцу транслитерации
   остальных 215 id того же файла; ни в одной записи (включая
   `ambiguity_registry`) эти id больше нигде не упоминались, так что
   переименование ничего не порвало.

`ThesaurusEntry.category`/`.service` — `TextChoices`, продублированные в
Python из `meta.categories`/`meta.services` файла (не читаются из JSON
на лету) — риск дрейфа при будущем редактировании файла закрыт тестом
`test_python_categories_match_json_meta_categories`/`..._services` в
`tests/test_thesaurus_file_integrity.py`: он же — регрессионный страж
структуры файла (валидный JSON, нет дублей id, id — валидные slug,
canonical уникален без учёта регистра, каждая запись имеет хотя бы один
short_form/synonym, `ambiguity_registry` не ссылается на несуществующие
id) на каждый прогон CI, а не разовая проверка при написании кода.

**TH-07 — частично реализовано, по итогам ревью.** `draft -> verified`/
`rejected` — admin-действия (`ThesaurusEntryAdmin.mark_verified`/
`mark_rejected`), которые (1) проверяют роль оператора (изначально
Куратор или Администратор — `_can_curate`; с упразднением роли «Куратор
службы» это Контролёр/Юрист или Администратор — `_can_verify`, см.
«Упразднение роли «Куратор службы»» выше), (2) пишут WORM-запись аудита
(`AuditLog.EventType.THESAURUS_UPDATED`) с оператором и diff
старого/нового статуса на каждое реальное изменение (повторное действие
на уже подтверждённой записи — no-op, аудит не пишется). Оба пункта были
проверены тестами (`tests/test_admin.py`) после того, как обнаружилось,
что первая версия действий (до ревью) статус меняла через голый
`queryset.update()` без аудита и без проверки роли вовсе.

**Решено Заказчиком: текущая модель остаётся.** Любой Контролёр/Юрист
может верифицировать записи тезауруса любой службы, не только своей —
ограничение TH-07 до СЛУЖБЫ-ВЛАДЕЛЬЦА (`ThesaurusEntry.service`)
сознательно не вводится (решение принято ещё когда роль называлась
«Куратор» — по существу не изменилось с переносом функционала на
Контролёра/Юриста). Роль (Контролёр/Юрист/Администратор) и WORM-аудит
операции (оператор + diff) остаются единственной проверкой — этого
достаточно. Дорабатывать не нужно: у `User` по-прежнему нет поля,
хранящего «Контролёр/Юрист — какой именно службы» (только `department`),
и вводить его для этого сценария не требуется.

**`ambiguity_registry` файла теперь персистится отдельной моделью
`ThesaurusAmbiguity`** (было — только транзитно при импорте, для
TH-02/TH-03). Раньше это было сознательно отложено («когда появится
модуль поиска, реестр нужно будет либо читать из того же JSON при
индексации, либо перенести в отдельную модель — это решение стоит
принимать вместе с дизайном самого поискового модуля, не раньше») — см.
следующий раздел, этот момент настал.

## Smart Search — сам поиск (ТЗ 4.4.1, `apps/search_ocr/search.py`)

Словарь терминов (выше) был готов и провалидирован; в этой партии
реализован сам поисковый модуль: расширение запроса по тезаурусу
(`expand_query`) и полнотекстовый поиск по карточкам НРД
(`search_documents`) с гибридным ранжированием. Web GUI —
`apps/search_ocr/{views,forms}.py`, `templates/search_ocr/search.html`,
смонтирован на `/` (домашняя страница Web GUI — на неё уже ссылалась
шапка `templates/base.html` до появления самой страницы;
`LOGIN_REDIRECT_URL` теперь `search_ocr:search` вместо временного
`core:styleguide`).

**Формула ранжирования — дословно ТЗ 2.2 §4.4.1** (текст получен и
реализован по итогам ревью; более раннее решение этой сессии — см.
историю коммитов — было самостоятельной приближённой формулой, честно
помеченной как требующая сверки с оригиналом; сверка проведена, формула
приведена в соответствие):

```
score = ExactMatch(reg_number) * 1.0
      + FTS(title)             * 0.8
      + FTS(summary)           * 0.5
      + FTS(ocr_body)          * 0.2
```

`ExactMatch(reg_number)` — точное совпадение (регистронезависимо) номера
документа с одним из терминов поиска. `FTS(поле)` — `SearchRank` по
`SearchVector` ЭТОГО поля отдельно (`config="russian"`), **не** общий
вектор с внутренними весами Postgres A/B/C/D — веса полей теперь берутся
из самой формулы ТЗ на уровне Python/SQL-выражения, а не из
Postgres-механизма ранжирования по позиции.

**Расширение по тезаурусу — НЕ отдельное слагаемое формулы**, а
подмешивается ВНУТРЬ каждого компонента, как прямо потребовал Заказчик:
список терминов поиска = `[сам запрос пользователя (вес 1.0)]` +
`expand_query(запрос)` (веса по TH-06 — см. ниже). Каждый термин
проверяется на точное совпадение с `reg_number` (вклад в `ExactMatch`,
берётся максимум по всем терминам через SQL `GREATEST`) и участвует в
полнотекстовом поиске по каждому из `title`/`summary`/`ocr_body` — вклад
`термин.weight * ts_rank(поле, термин)` суммируется по всем терминам
(`ts_rank` не позволяет взвесить отдельные лексемы внутри одного
`tsquery`, поэтому суммирование по терминам делается вручную отдельными
`SearchRank`-аннотациями), затем сумма домножается на вес поля.
Прямой запрос ищется как `websearch_to_tsquery` (свободный
пользовательский текст); термины расширения — как `phraseto_tsquery`
(устойчивые словосочетания тезауруса, должны совпадать как фраза, не как
«слова где угодно в документе»).

`ocr_body` (`apps/documents/models.py`) заполняется асинхронно конвейером
OCR (Этап 3, `apps/documents/tasks.py` — см. раздел «Конвейер OCR» ниже)
при загрузке/замене `files_original`. **Честная граница**: до завершения
задачи (или для документов, загруженных до появления конвейера и ни разу
не пересохранённых с новым файлом) поле пусто — безопасно: пустое поле
просто не даёт вклада в `FTS(ocr_body)`, не создаёт ложных совпадений;
ретроактивного массового запуска OCR по уже существующим документам в
этой партии нет (см. честные границы конвейера ниже).

**Веса терминов расширения** — TH-06 (`validation_rules` файла) взято
дословно: `short_forms`/`synonyms` дают вес `ThesaurusEntry.weight`
(по умолчанию 1.0), `synonyms_legacy` — **фиксированный** вес 0.3
(дословно "synonyms_legacy расширяют запрос только с весом 0.3", не
`entry.weight * 0.3`). Расширение использует ТОЛЬКО записи со
`status=VERIFIED` — неподтверждённые/отклонённые записи не должны менять
результаты поиска для всех пользователей (тот же принцип, что уже был
у TH-07 при верификации в админке).

**Разрешение неоднозначности** (`ambiguity_registry` файла, например «ТП»
→ тяговая подстанция / транспортное происшествие / трамвайный парк
legacy) использует ТОЛЬКО структурированную часть данных — вес кандидата
и сопоставление опциональных фасетов (категория/служба, доступны в
форме поиска) с полями `.category`/`.service` самого́ кандидата-записи
тезауруса. Свободный текст поля `disambiguation` (например «при фильтре
service=EKH → тяговая подстанция») **НЕ разбирается программно** — это
произвольная русская проза без формального DSL для каждой записи
реестра, парсинг такого текста был бы хрупкой NLP-эвристикой, а не
инженерным решением; хранится как есть для отображения/аудита. Если
фасет совпадает с полем кандидата — кандидат получает вес 1.0
(однозначно выбран), иначе используется его собственный вес из реестра
(все смыслы добавляются в расширение пропорционально вероятности).

**`ThesaurusAmbiguity`/`ThesaurusAmbiguityCandidate` — по итогам ревью
пересмотрено с JSONField на настоящую связь.** Первая версия этой
партии хранила `candidates` как `JSONField` (список `{id, weight,
reason}`) прямо на `ThesaurusAmbiguity` — работало, но `id` кандидата
был просто строкой внутри JSON, без референциальной целостности на
уровне БД (удаление `ThesaurusEntry` не подчистило бы такую JSON-ссылку)
и без индексированного пути «запись тезауруса -> её неоднозначности»
(`apps.search_ocr.search.expand_query()` вынужден был бы каждый раз либо
сканировать всю таблицу `ThesaurusAmbiguity`, либо парсить JSON). Теперь
— отдельная модель `ThesaurusAmbiguityCandidate` (`ambiguity` FK,
**`entry` FK на `ThesaurusEntry`**, `weight`, `reason`,
`UniqueConstraint(ambiguity, entry)`, `Index(fields=["entry"])`);
`import_thesaurus()` синхронизирует её по принципу «полная замена набора»
(upsert присутствующих в файле кандидатов, удаление пропавших между
импортами). `expand_query()` читает `entry.ambiguity_candidates`
(обратная связь через тот же индексированный FK, `prefetch_related` —
без дополнительного запроса на каждую запись тезауруса).

**Доступ к ДСП** — `search_documents()` фильтрует `access_level=RESTRICTED`
для пользователей без `dsp_access`/не суперпользователей: то же правило,
что и в `NormativeDocumentAdmin.get_queryset()`, продублировано
осознанно — поиск отдельная точка входа к тем же данным, не должен
полагаться на проверку допуска где-то выше по стеку.

**Черновики (status=DRAFT) исключены из результатов поиска** —
**самостоятельное, НЕ подтверждённое Заказчиком допущение**: «база
знаний» ищет то, что когда-либо было официально зарегистрировано, а не
рабочие черновики. Не вычитано из ТЗ буквально — если это неверно,
нужно явное решение Заказчика, не молчаливое исправление задним числом.
Ранние формулировки такого правила (в других системах/шаблонах) иногда
делают исключение «черновик виден куратору» — в этом проекте роль
«Куратор службы» упразднена (см. «Упразднение роли «Куратор службы»»
выше), замены ей для этого конкретного случая Заказчик не называл, и
самостоятельно она не придумана: черновики сейчас исключены из поиска
единообразно для всех, без исключений по роли.

**Индекс вычисляется на лету, не персистится.** Формула требует ТРИ
отдельных `SearchVector` (`title`/`summary`/`ocr_body`, каждый своим
весом из формулы, не общий вектор с внутренними весами Postgres A/B/C/D
— см. выше), все строятся в каждом запросе поиска
(`django.contrib.postgres.search`), без персистентных
`SearchVectorField`/`GinIndex` и без фоновой переиндексации — в отличие
от `loading_notes.index_rebuild` файла тезауруса («После загрузки —
асинхронная переиндексация расширенного словаря и сброс кэша поисковых
подсказок (Redis)»), которая относится к словарю терминов при импорте,
не к индексу самих карточек НРД. При текущем небольшом объёме документов
это не проблема производительности; персистентный индекс
(`SearchVectorField` × 3 + `GinIndex` + обновление в
`NormativeDocument.save()` или через сигнал) — естественное развитие
для Этапа 3/4 при росте объёма базы, преждевременно сейчас (тот же
принцип, что и у остальных «пока не оптимизировано под масштаб» мест
проекта).

**Ограничение числа терминов расширения** (`MAX_EXPANDED_TERMS = 5`,
`apps/search_ocr/search.py`) — каждый термин расширения даёт 1
(`ExactMatch`) + 3 (`title`/`summary`/`ocr_body`) `SearchRank`/`Case`-
аннотаций (отдельный проход `tsquery` по вычисляемому на лету
`SearchVector` для каждого поля); без границы запрос, совпадающий с
большим числом записей тезауруса, дал бы неограниченно тяжёлый
SQL-запрос на один HTTP-запрос пользователя. Значение снижено с 8 (было
в приближённой версии формулы с одним общим вектором) до 5 — цена
одного термина расширения утроилась с переходом на три отдельных поля.

**External API поиска — есть** (`apps/search_ocr/api.py`,
`GET /api/v1/search/documents/`, `DocumentSearchAPIView`). В партии
самого поиска его сознательно не заводили («заводить пустой `api.py` без
согласованного контракта — опережение, а не экономия»); добавлен
отдельной задачей, как и планировалось, и, как и обещано, использует тот
же `search.py` — бизнес-логика не продублирована, HTTP-слой только
валидирует ввод той же `SearchForm` и отдаёт постраничный JSON.
Троттлинг — `SearchApiThrottle` (30 запросов/мин на IP, см. «Троттлинг
HTTP» ниже): поисковый запрос дороже обычного чтения (расширение по
тезаурусу + три FTS-поля), поэтому у него отдельный, более жёсткий лимит.

**Пагинация результатов — есть.** Web GUI: `Paginator`, `PAGE_SIZE = 20`
(`apps/search_ocr/views.py`), навигация в шаблоне сохраняет параметры
фильтров (`query_string` без `page`). External API: `PageNumberPagination`,
`page_size = 20`, `max_page_size = 50` (клиент может запросить меньше
через `page_size`, но не больше — верхняя граница защищает от запроса
всей базы одной страницей). Прежний жёсткий `MAX_RESULTS = 50` без
навигации снят: он был компромиссом «достаточно для небольшой текущей
базы», а не целевым поведением.

**Ограничение размера запроса** (`apps/search_ocr/forms.py`,
`clean_q`): `MAX_QUERY_LENGTH = 200` символов и `MAX_QUERY_TERMS = 12`
слов. Это не косметика: каждый термин запроса после расширения по
тезаурусу превращается в несколько FTS-выражений в SQL (см. формулу
выше), поэтому длина запроса напрямую умножает стоимость плана. Лимит
проверяется в форме — то есть одинаково для Web GUI и External API,
которые обе через неё проходят.

## Конвейер OCR (Этап 3, `apps/documents/ocr.py`, `apps/documents/tasks.py`)

Распознавание скана НРД — под `FTS(ocr_body)` формулы ранжирования Smart
Search выше (пока не реализовано на момент написания того раздела, теперь
реализовано).

**Точка запуска** — `NormativeDocument.save()` (`apps/documents/models.py`):
тот же принцип "сравнить значение поля до/после `super().save()`", что уже
использовался для `retention_category`/`status` (см. «Целостность данных»
выше), применён к `files_original`. При первой загрузке скана и при каждой
его замене задача `run_ocr_for_document` ставится в очередь Celery через
`transaction.on_commit(lambda: run_ocr_for_document.delay(str(pk)))` — не
напрямую внутри `save()`, потому что воркер читает файл и строку БД
отдельным соединением/процессом: если поставить задачу в очередь до
коммита транзакции, воркер рискует не увидеть ни файл, ни саму запись.
Карточки без файла (`bool(self.files_original)` ложно — в фикстурах/тестах
`files_original` нередко не заполняется, хотя по ТЗ обязателен) явно
исключены из триггера — иначе почти весь существующий набор тестов начал
бы безуспешно гонять OCR по несуществующим файлам на каждом
`make_document()`.

**Извлечение текста** (`apps/documents/ocr.py`, `extract_text_and_confidence`)
— чистая функция без побочных эффектов (не знает о Django ORM/Celery),
поэтому тестируется напрямую, без брокера и без реального документа в БД
(`apps/documents/tests/test_ocr.py` — по-настоящему **не замоканные**
тесты: реально вызывают `pdf2image`/poppler и `pytesseract`/Tesseract на
PDF, сгенерированном на лету через Pillow из Cyrillic-текста шрифтом
DejaVu Sans). Страницы обрабатываются **пакетами** (`batch_size=10` по
умолчанию), а не все сразу: `pdf2image.pdfinfo_from_bytes` даёт число
страниц, затем `convert_from_bytes(..., first_page=N, last_page=M)` в цикле
— при лимите ТЗ 1.2 §4.2.1 на скан-оригинал (150 МБ, потенциально сотни
страниц) растеризация всего файла разом держала бы в памяти все страницы
одновременно; пакет ограничивает пик памяти своим размером независимо от
общего числа страниц. `pytesseract.image_to_string`/`image_to_data`
распознаёт текст и уверенность каждой страницы (200 DPI). Средняя
уверенность — **по словам, а не по страницам** (word-count-weighted):
простое среднее постраничных средних придало бы короткой странице такой же
вес, как длинной. Строки уровня «блок/абзац/строка» в `image_to_data` (не
«слово») имеют пустой `text` — фильтруются по нему; уверенность реально
распознанного слова (в т.ч. низкая, вплоть до 0) не отбрасывается. Шкала
уверенности Tesseract — уже 0-100, ровно то, под что изначально заведены
валидаторы `NormativeDocument.ocr_confidence` (`MinValueValidator(0)`/
`MaxValueValidator(100)`) — не совпадение, поле исходно заводилось под эту
шкалу.

**Предобработка страницы перед OCR** (`apps/documents/ocr_preprocessing.py`,
`preprocess_page`, включена по умолчанию, ТЗ 2.2 §4.5) — без неё пороги
качества ниже (особенно пониженный порог архивного фонда) на
пожелтевшем/перекошенном скане недостижимы:
- автовыравнивание перекоса, ограничено ±15° (`cv2.minAreaRect` по маске
  текста; угол меньше 0.5° игнорируется — сам поворот внёс бы больше шума,
  чем перекос);
- подавление шума/перфорации — `cv2.fastNlMeansDenoising` +
  морфологическое **закрытие** (`MORPH_CLOSE`) небольшим ядром. Явно НЕ
  открытие (`MORPH_OPEN`), которое было в исходном предложении ревью:
  текст скана тёмный на светлом фоне, значит перфорация/пыль — это мелкие
  ТЁМНЫЕ точки на светлом фоне; убрать именно такие точки, не тронув
  штрихи шрифта, — задача закрытия, открытие для этой полярности
  изображения только увеличивает шум (проверено на синтетическом тесте,
  `apps/documents/tests/test_ocr_preprocessing.py::DenoiseTests`, а не
  предположение на словах);
- адаптивная бинаризация — Otsu по умолчанию (дешевле, устойчивее на
  однородном фоне современных НРД) или Sauvola явным выбором
  (`binarize_method="sauvola"`, лучше держит неоднородный фон архивных
  сканов); ТЗ называет оба метода, не указывая, какой когда — выбор
  метода на конкретный документ не автоматизирован (честная граница,
  ниже).

**Язык — только русский** (`settings.OCR_LANGUAGE`, по умолчанию `rus`) —
весь корпус НРД ГЭТ на русском; домен-специфичные сокращения и термины
уже разбирает тезаурус Smart Search (`apps/search_ocr`), а не сам OCR.
Честная граница: многоязычные документы/сканы не поддерживаются.

**Дифференцированные пороги качества по категории** (`apps/documents/ocr_thresholds.py`,
ТЗ 2.2 §4.4.2) — `NormativeDocument.ocr_category` (`OcrCategory`:
`modern_nrd`/`mixed_forms`/`archive`/`schemes`, пусто допустимо) и
`ocr_status` (`OcrStatus`: `not_processed`/`indexed`/`needs_review`).
`get_threshold_for_document()` берёт явную категорию карточки, а если её
нет — выводит `modern_nrd`/`archive` по году `reg_date` (граница — 2018);
`mixed_forms`/`schemes` автоматически не выводятся никогда (дата не
говорит, бланк это или схема) — их должен проставить человек при
регистрации. После распознавания `run_ocr_for_document` сравнивает
`ocr_confidence` с порогом и выставляет `ocr_status`; `confidence=None`
(ни одного распознанного слова) — заведомо `needs_review`.

Пороги («Min OCR Score» из таблицы ТЗ): `modern_nrd` — 90, `mixed_forms` —
75, `archive` — 65, `schemes` — 80. **Не опечатка, а два разных числа для
архива**: ТЗ отдельно называет порог ручной верификации для архивного
фонда — 75, отличный от его же нижней границы приемлемого результата — 65;
`OcrThreshold.review_below` держит их раздельно (`min_score=65,
review_below=75`), у остальных категорий `review_below` по умолчанию
совпадает с `min_score`, так как ТЗ отдельного числа для них не называет.

ЧЕСТНЫЕ ГРАНИЦЫ дифференцированных порогов:
- **Top-3** (доля документов, где верное значение входит в тройку
  кандидатов) — метрика из той же таблицы ТЗ, не реализована и не может
  быть посчитана на этом пайплайне в принципе: `pytesseract`/Tesseract
  отдаёт одно распознанное слово на позицию, а не набор альтернативных
  кандидатов с вероятностями — измерять Top-3 нечем без смены движка.
- **«Схемы и чертежи»**: ТЗ требует «Индексация штампа (ГОСТ 2.104).
  Графика не индексируется» — не реализовано, распознаётся вся страница
  целиком (см. «Извлечение текста» выше); выделение и распознавание только
  области штампа потребовало бы отдельного шага детекции региона на
  странице, которого сейчас нет. Порог категории применяется к
  распознаванию всей страницы, а не только штампа.
- Выбор метода бинаризации (Otsu/Sauvola) на документ не автоматизирован
  — всегда Otsu, если явно не передать `binarize_method="sauvola"`
  (сейчас код нигде не передаёт).

**Retry, таймауты и аудит** (`apps/documents/tasks.py`, `run_ocr_for_document`,
`bind=True, max_retries=3, time_limit=600, soft_time_limit=540`) — любая
ошибка на чтении файла/распознавании (повреждённый PDF, временная
недоступность MinIO/диска, `SoftTimeLimitExceeded` на зависшей/слишком
медленной для лимита ТЗ 1.2 §4.2.1 (150 МБ) задаче) ведёт к повтору через
`self.retry()`, пока `self.request.retries < self.max_retries`; после
исчерпания повторов — **одна** финальная запись
`AuditLog.EventType.DOCUMENT_OCR_FAILED` в WORM-журнал (не на каждую
промежуточную попытку, иначе один проблемный документ дал бы несколько
записей на одно по сути событие) и `ocr_status=needs_review` (документ без
единого распознанного символа однозначно требует ручного внимания — тот
же статус, что и у низкой уверенности, не отдельное «необработан»).
Мягкий таймаут (`SoftTimeLimitExceeded`) ловится тем же `except Exception`,
что и остальные сбои — сохранения частичного результата уже
растеризованных страниц на мягком таймауте нет (честная граница, не
усложняем без явной необходимости). Успех — `.filter(pk=...).update(...)`
(не `.save()`: системная фоновая запись результата не должна сама себя
повторно поставить в очередь и не относится к тем полям, что вызывают
обязательный аудит смены статуса/категории в `NormativeDocument.save()`)
плюс запись `DOCUMENT_OCR_COMPLETED` (детали включают применённый порог
`review_threshold` и итоговый `ocr_status`). Карточка, удалённая между
постановкой задачи в очередь и её выполнением, — тихий no-op (лог
предупреждения, без аудита и без retry: повторять уже нечего).

**Ретроактивный запуск** — `python manage.py rerun_ocr [--limit=N]
[--force]` (`apps/documents/management/commands/rerun_ocr.py`): без
`--force` ставит в очередь только карточки с файлом и
`ocr_status=not_processed` (документы, загруженные до появления конвейера
— `save()` ставит задачу только на фактическое изменение
`files_original`, а не на существование старой записи); `--force`
перераспознаёт вообще все карточки с файлом, включая уже
`indexed`/`needs_review` (например, после смены движка/порогов/языка).

**Брокер — Redis** (БД 0), уже был предусмотрен в стеке (`docker-compose.yml`,
`.env.example`) заранее, но не использовался кодом до этой партии.
`CELERY_TASK_ALWAYS_EAGER=True`/`CELERY_TASK_EAGER_PROPAGATES=True`
включаются в тестовом режиме (`"test" in sys.argv`,
`config/settings/base.py`) — весь набор тестов проекта (включая тесты
других приложений, создающие документы через `make_document()`) не
поднимает реальный брокер.

**Result backend — отдельная БД Redis (1-я, не та же, что у брокера)**,
`CELERY_RESULT_EXPIRES=3600`. Приложение по-прежнему нигде не делает
synchronous `task.get()` — воркер сам пишет результат в БД и WORM-аудит
(выше); backend добавлен ради операционной интроспекции состояния задач
(`AsyncResult`, `celery inspect`/Flower), а не потому что код его читает
— честно говоря, ценность пока инфраструктурная/на будущее, не
задействованная функциональностью этой партии.

**Воркер как systemd-сервис** (`deploy/systemd/get-celery-worker.service`)
— шаблон юнита для целевой платформы (Debian 12 Bookworm, см. «Платформа
развёртывания» выше): `celery -A config worker -l info -c 4`,
`Restart=always`. ЧЕСТНАЯ ГРАНИЦА: шаблон не проверен вживую на целевой ОС
(в песочнице разработки нет systemd-контура, см. «Локальная разработка в
этой сессии» ниже) — пути/пользователь/число воркеров нужно свести с
реальным сервером перед вводом в опытную эксплуатацию, как и остальные
шаблоны `deploy/*` в этом репозитории (Prometheus/Grafana provisioning).

**Честные границы**:
- Нет UI прогресса распознавания/очереди — статус виден только через
  `ocr_body`/`ocr_confidence`/`ocr_status` и WORM-журнал, отдельного экрана
  мониторинга конвейера нет; result backend (выше) даёт интроспекцию через
  внешние инструменты (Flower и т.п.), не через Web GUI проекта.
- `docker-compose.yml` не заводит отдельный контейнер для воркера — само
  приложение (веб) в этом docker-compose тоже не контейнеризовано (см.
  «Локальная разработка в этой сессии» ниже), воркер запускается локально
  командой `celery -A config worker -l info` (README «Локальный запуск»)
  либо через systemd-шаблон выше на целевой ОС.
- CI (`.github/workflows/ci.yml`) устанавливает `tesseract-ocr`,
  `tesseract-ocr-rus`, `poppler-utils`, `fonts-dejavu-core` через apt перед
  прогоном тестов — `test_ocr.py` реально вызывает Tesseract, а не мокает
  его; брокер/result backend Redis в CI не поднимаются (не нужны при
  `TASK_ALWAYS_EAGER`). `opencv-python-headless` — чистый pip-пакет, без
  дополнительных системных библиотек в этой песочнице (headless-сборка,
  без зависимостей от X11/GTK, которые нужны были бы полной `opencv-python`).

## Анти-фрод / контроль целостности загрузки (Этап 3, ТЗ 4.7)

Первый пункт из README «Дальше по плану» после конвейера OCR — два
независимых честных пробела из раздела «Вход и 2FA/TOTP» выше закрыты.

### Rate limiting / lockout (`apps/iam/services.py`)

`LOCKOUT_MAX_ATTEMPTS = 5`, `LOCKOUT_WINDOW = 15 минут` — не новые числа:
буквально те же, что уже вшиты в Grafana-алерт «5+ неудачных попыток
подряд» (`deploy/grafana/provisioning/alerting/audit-alerts.yml`, group by
`actor_personnel_number`, `INTERVAL '15 minutes'`, `HAVING COUNT(*) >= 5`).
Теперь тот же порог не только сигналит постфактум, но и реально
блокирует вход.

Источник данных — уже существующий `AuditLog.EventType.SESSION_LOGIN_FAILED`
(скользящее окно, `COUNT(*)` за 15 минут по `actor_personnel_number`), без
новой инфраструктуры: осознанно не заведены Redis-счётчики — контур входа
не должен зависеть от доступности Redis (в отличие от конвейера OCR, где
Redis уже жёсткая зависимость, но НЕ на критическом пути входа
пользователей). `is_locked_out()` проверяется в `check_credentials()` (шаг
1, пароль) и `verify_totp_login()` (шаг 2, TOTP-код) — **один общий
счётчик на оба шага**, ТЗ формулирует лимит как «подбор пароля ИЛИ
TOTP-кода», не два независимых порога. Проверка — ДО `authenticate()`/
`verify_totp_code()`: верный пароль/код тоже не проходит при активной
блокировке, иначе это было бы не блокировкой учётной записи, а только
ограничением на подбор.

`LoginBlocked` (новое исключение) поднимается вместо `None` — вызывающий
код (Web `views.py`, API `api.py`) показывает отдельное сообщение
«Слишком много неудачных попыток входа», статус `429 Too Many Requests`
в API. Это не утечка данных: счётчик неудач пишется независимо от того,
существует ли табельный номер вообще (`check_credentials()` уже писал
`SESSION_LOGIN_FAILED` для несуществующих номеров и раньше), так что
факт блокировки сам по себе не подтверждает существование учётки.

Попытка ВО ВРЕМЯ блокировки не пишет новую запись `SESSION_LOGIN_FAILED`
— иначе блокировка самопродлевалась бы бесконечно от самого факта
повторных попыток вместо того, чтобы сняться по истечении скользящего
окна (самая старая неудача просто "стекает" за пределы 15 минут — нет
отдельного таймера/шага сброса).

**Второй, независимый контур — по IP** (по замечанию ревью: одна
учётка со множества IP не единственная форма перебора, есть ещё
энумерация множества табельных номеров с одного источника).
`IP_LOCKOUT_MAX_ATTEMPTS = 20`, то же 15-минутное окно
(`IP_LOCKOUT_WINDOW = LOCKOUT_WINDOW`) — **не число из ТЗ**, решение этой
партии: явно выше персонального порога (5) в 4 раза, чтобы легитимный
общий терминал/NAT с несколькими сотрудниками не блокировался от
обычных опечаток, но массовый перебор с одного источника — блокировался.
Источник — тот же `AuditLog.EventType.SESSION_LOGIN_FAILED`, но фильтр
по `details__ip_address` (JSONField, без Redis, тем же принципом, что и
персональный счётчик) вместо `actor_personnel_number`. `is_ip_locked_out()`
проверяется НАРЯДУ с `is_locked_out()` на каждом шаге (пароль, TOTP) —
`LoginBlocked` поднимается, если сработал любой из двух контуров;
**второй контур не заменяет первый**, оба активны одновременно.
`_client_ip(request)` — `request=None` (юнит-тесты сервисного слоя без
HTTP-запроса) отключает IP-контур, не роняет вызов.

**Честная граница IP-контура**: `details__ip_address=...` — JSONField-
запрос через `->>` без специализированного (GIN/expression) индекса —
не оптимизировано так же, как персональный счётчик (у него есть
`audit_lockout_window_idx`, композитный B-tree индекс
`(event_type, actor_personnel_number, created_at)` — равенства первыми,
диапазон последним, под форму именно этого запроса).

**`Retry-After` в ответе** — по замечанию ревью (RFC 6585/9110,
стандартная практика для 429). Скользящее окно, не фиксированный таймер
— момент снятия блокировки нетривиален: снимается не когда истекает
самая СТАРАЯ неудача, а когда самая СТАРАЯ из последних `MAX_ATTEMPTS`
неудач выходит за окно (лишние неудачи сверх порога не откладывают этот
момент дальше). `services._window_expires_at()` находит именно N-ю с
конца неудачу и считает её `created_at + window`;
`login_retry_after_seconds()` берёт максимум из личного и IP-таймера
(если сработали оба контура — ждать до более позднего). API (`api.py`,
оба шага) отдаёт заголовок `Retry-After: <секунды>` при 429; Web-контур
заголовок не выставляет (нет HTTP-семантики Retry-After у HTML-страницы
с формой, сообщение об ошибке то же самое текстом).

### Антивирусная проверка (`apps/core/antivirus.py`)

ClamAV (clamd) был поднят в `docker-compose.yml` с Этапа 1 «для раннего
тестирования интеграции» (его собственный комментарий), но код его не
вызывал до этой партии. `scan_file()` — тонкая обёртка над пакетом
`clamd` (протокол INSTREAM по TCP).

**Точка встраивания — синхронно, внутри `save()`, ДО `super().save()`**
(`NormativeDocument.save()`: `files_original`/`files_editable`;
`Template.save()`: `file_editable`/`file_sample`) — **осознанное отличие**
от того, как в этом же `NormativeDocument.clean()` уже проверяется
`retention_category` (та проверка работает только через `full_clean()`,
то есть только при прохождении через форму/admin, и молча не применяется
к `.objects.create()`). Для антивируса это неприемлемо: последствие
пропуска (заражённый файл в WORM-защищённом бакете `originals`, откуда
его потом может быть невозможно удалить до истечения срока хранения) на
порядок серьёзнее, чем у некорректной `retention_category` (данные
можно поправить и после факта). Поэтому проверка — в `save()`,
применяется универсально, независимо от того, идёт ли запись через
форму, admin или программное создание.

`needs_scan(field_file)` — сканирует только **новую, ещё не сохранённую в
хранилище** загрузку (`FieldFile._committed is False`, то есть полю
присвоен реальный `File`/`UploadedFile`). Присвоение строки-имени
(тесты/фикстуры, загрузка существующей записи из БД) не запускает
сканирование — сканировать нечего, в хранилище ничего нового не
добавляется; без этого разбора почти весь существующий набор тестов
проекта (везде, где `files_original="path/to/file.pdf"` задаётся строкой)
требовал бы живого clamd на каждый `make_document()`.

`AntivirusUnavailable` (clamd недоступен/ответил не по протоколу) **тоже
блокирует сохранение** — fail-closed, не fail-open: непроверенный файл не
должен попасть в неизменяемое хранилище только потому, что антивирус
временно не отвечает. Отказ входа при недоступности Redis (см. rate
limiting выше) и отказ загрузки при недоступности ClamAV — разные
решения для разных рисков: ошибочно заблокировать ВСЕМ пользователям вход
из-за временной недоступности инфраструктуры намного хуже, чем временно
не принимать новые файлы.

Обнаружение сигнатуры — новая WORM-запись `AuditLog.EventType.UPLOAD_MALWARE_DETECTED`
(поле, сигнатура, тип/id объекта) — пишется из `apps/core/antivirus.py`
(`scan_uploaded_field()`), не из моделей: единая точка для обеих моделей
(`NormativeDocument`, `Template`), чтобы правило "что считается событием
безопасности" не разъехалось между ними, тот же принцип, что уже
применялся для входа (`apps/iam/services.py` пишет аудит из одной общей
функции для Web и API).

**Тесты — по-настоящему живой ClamAV**, тем же принципом, что и Tesseract
для OCR: `apps/core/tests/clamd_fixture.py` поднимает собственный `clamd`
(системный пакет `clamav-daemon`, не Docker) с одной кастомной `.hdb`-
сигнатурой на EICAR-тестовую строку (https://www.eicar.org/, отраслевой
стандарт для тестирования антивирусов — не вредоносный код) — без
`freshclam`/обращения к внешним базам сигнатур, быстро и детерминированно
что локально, что в CI. Демон стартует один раз на класс тестов
(`setUpClass`), слушает нестандартный TCP-порт (13310), не пересекается с
портом ClamAV из `docker-compose.yml` (3310).

**Честные границы**:
- Ограничение размера потока по умолчанию у ClamAV (`StreamMaxLength
  25M`) меньше лимита ТЗ 1.2 §4.2.1 на скан-оригинал (150 МБ) —
  `deploy/clamav/clamd.conf` поднимает лимит до 200 МБ. **Живо
  проверено** (по замечанию ревью) отдельным `clamd`, поднятым тем же
  тестовым фикстуром (`ClamdTestServer(stream_max_length=...)`) с малым
  лимитом (1M): поток ниже лимита (500 КБ) сканируется штатно, поток
  выше лимита (2 МБ) — не проходит НЕЗАМЕЧЕННЫМ как «чистый». На
  превышении `StreamMaxLength` сырой сокет `clamd`-пакета кидает
  `BrokenPipeError` (`OSError`, не собственное исключение пакета
  `clamd`) — подтверждено, что уже существующий
  `except (clamd.ClamdError, OSError)` в `scan_file()` корректно ловит
  и этот случай, превращая его в `AntivirusUnavailable` (fail-closed, не
  тихое «чисто»). Регрессионный тест —
  `apps/core/tests/test_antivirus.py::StreamMaxLengthTests`, оставлен
  навсегда, не разовая проверка.
- Нет проверки архивов на превышение `MaxScanSize`/защиту от zip-бомб
  сверх того, что уже включено дефолтами ClamAV (`ScanArchive true` и
  т.п.) — отдельно не настраивалось и не проверялось.
- Сканируется весь файл целиком синхронно при каждой загрузке/замене —
  для файла, близкого к лимиту 150/200 МБ, это ощутимая синхронная
  задержка `save()` (в отличие от OCR, вынесенного в Celery); осознанный
  компромисс ради fail-closed гарантии (см. выше), не оптимизировано под
  латентность. **Проверено (по замечанию ревью)**, что эта задержка не
  усугубляется удержанием открытой БД-транзакции: ни один вызывающий код
  не оборачивает `NormativeDocument.save()`/`Template.save()` в
  `transaction.atomic()` снаружи, а сама проверка (антивирус + макросы,
  см. ниже) стоит ДО того, как `save()` открывает СВОЙ внутренний
  `atomic()`-блок (если он вообще есть) — соединение с БД не удерживается
  захваченным на время синхронного сетевого обмена с `clamd`.

### Проверка на макросы/ActiveX (`apps/core/macro_check.py`)

По замечанию ревью: ClamAV детектирует ИЗВЕСТНЫЕ вредоносные макросы по
сигнатурам, но не сам факт наличия VBA/ActiveX-кода в файле — новый,
незнакомый сигнатурной базе макрос пройдёт мимо `antivirus.py`
незамеченным. `contains_macros()` — структурная проверка ZIP-контейнера
DOCX/XLSX (`word/vbaProject.bin`, `xl/vbaProject.bin`,
`word/vbaData.xml`, `xl/vbaData.xml`, `word/activeX/*`, `xl/activeX/*`)
через `zipfile`, без сигнатурных баз — сам факт присутствия одного из
этих путей в архиве уже значит «в документе есть макрос/ActiveX-объект»,
независимо от того, вредоносен ли он.

**Точка встраивания** — та же, что у антивируса: `NormativeDocument.save()`/
`Template.save()`, сразу ПОСЛЕ `antivirus.scan_uploaded_field()` для того
же поля, тем же fail-closed принципом (`reject_if_has_macros()` поднимает
`MacrosDetected`, `save()` не идёт дальше) и тем же гейтингом через
`FieldFile._committed` (`needs_scan()`), что и антивирус — не
пересканирует уже сохранённые файлы/строковые фикстуры тестов. Отказ
пишет новую WORM-запись `AuditLog.EventType.UPLOAD_MACRO_REJECTED`
(поле, список найденных маркеров) — ДО отказа `save()`, тем же принципом,
что и `UPLOAD_MALWARE_DETECTED`.

**Честная граница**: только OOXML (DOCX/XLSX, `zipfile.ZipFile`) —
легаси-форматы `.doc`/`.xls` (OLE Compound File, не ZIP) не
распознаются как контейнер и просто не считаются содержащими макросы
(`zipfile.BadZipFile` → пустой список маркеров, не ошибка). Осознанно
не сделано: ТЗ-БЗ-ГЭТ-2026-V2.2 §4.2.1 требует проверку именно
DOCX/XLSX для `files_editable`, легаси-форматы вне области требования
этой партии — проверка легаси потребовала бы отдельной библиотеки
(`olefile`) и отдельного разбора внутренней структуры OLE, не сделано.

## Web GUI + External API — два независимых контура (Этап 2)

Первый HTTP-слой проекта: до этого были только модели, сервисы,
management-команды и Django admin. Первая попытка (см. историю коммитов)
завела единственный DRF+сессионный API-слой сразу под и Web, и API —
**пересмотрено по итогам ревью, решение Заказчика:**

- **Web GUI (внутренний, для сотрудников)** — Django Templates + HTMX +
  Alpine.js, серверный рендеринг, сессия + CSRF. Тянуть DRF+SPA под
  внутренний GUI означало бы удлинить сроки и усложнить сессии/2FA без
  реальной необходимости — внутри периметра клиент один (браузер
  сотрудника), не множество независимых интеграций.
- **External API (интеграции)** — DRF + `drf-spectacular` (OpenAPI) +
  JWT (`djangorestframework-simplejwt`). Голый Django Views не закрыл бы
  требование OpenAPI-документации и токен-аутентификации для внешних
  систем — им нужна не cookie-сессия конкретного браузера, а bearer-токен.

**DDD-граница (правило на все будущие app'ы, не только iam):** ни
`views.py` (Web), ни `api.py` (API) не обращаются к `Model.objects.*` и
не содержат бизнес-логику напрямую — только валидируют HTTP-ввод (через
`forms.py`/`serializers.py`), вызывают функции `services.py` и формируют
HTTP-ответ (HTML/redirect в Web, JSON в API). Целевая структура app'а с
обоими контурами:

```
apps/<domain>/
├── models.py       # данные
├── services.py      # бизнес-логика — ЕДИНСТВЕННОЕ место, где Model.objects.*
├── forms.py         # Django Forms — валидация ввода Web GUI
├── serializers.py    # DRF Serializers — валидация ввода External API
├── views.py         # Django CBV — HTML/redirect, сессия
├── api.py           # DRF APIView/ViewSet — JSON, JWT
└── urls.py + api_urls.py  # раздельный роутинг (пример — apps/iam)
```

`apps/search_ocr` пока не разложен в эту структуру — Smart Search (сам
поиск, не только словарь) ещё не реализован, заводить пустые
`forms.py`/`api.py` без реального содержимого было бы преждевременной
абстракцией. Структура — конвенция на будущее, когда до поиска дойдёт
очередь, не обязательство прямо сейчас.

### apps/iam — вход и 2FA/TOTP (ТЗ 4.7), первая реализация обоих контуров

Общая бизнес-логика — `apps/iam/services.py` (раздел «Вход и 2FA/TOTP» в
конце файла, отдельно от более старого `import_personnel`): `check_credentials()`,
`make_totp_pending_ticket()`/`verify_totp_login()`, `record_session_login()`/
`record_session_logout()`, `start_totp_enrollment()`/`confirm_totp_enrollment()`,
`user_auth_summary()`. Ни Web (`views.py`), ни API (`api.py`) не дублируют
эти правила — оба вызывают ровно эти функции.

**Двухшаговый вход одинаков в обоих контурах:** шаг 1 проверяет пароль и,
если у пользователя включена 2FA (`User.totp_enabled`), возвращает
подписанный тикет (`django.core.signing`, 5 минут на ввод кода) вместо
готовой авторизации; сама авторизация (`django_login()` в Web, выдача
JWT в API) происходит только в шаге 2, после верного кода. Тикет
подписан, не завязан на Django-сессию — поэтому шаг 2 одинаково
работает и для контура с cookie (Web хранит тикет во временной,
неавторизованной сессии), и для контура без состояния на сервере
(API/JWT — тикет целиком в теле JSON-ответа/запроса), одним и тем же
кодом. На шаге 2 пользователь ПЕРЕЧИТЫВАЕТСЯ из БД, не берётся из снимка
шага 1, и `is_active` проверяется заново — блокировка между шагом 1 и
шагом 2, пусть окно и небольшое (5 минут), не должна пропускать вход.

**Web** (`apps/iam/{views,forms}.py`, шаблоны `templates/iam/`, под
`/accounts/`): `login/` (форма) → `login/verify-totp/` (форма, если
нужно) → сессия. `logout/` — POST-only (Django 5-конвенция). 2FA
enroll/confirm — HTMX: кнопка «Начать подключение» на `totp/enroll/`
делает `hx-post` и получает фрагмент с секретом/URI и формой кода без
перезагрузки страницы; CSRF для hx-post ВНЕ `<form>` подставляется
глобальным обработчиком `htmx:configRequest` в `templates/base.html`
(иначе таким запросам неоткуда взять `{% csrf_token %}`).

**External API** (`apps/iam/{api,serializers}.py`, под `/api/v1/auth/`):
`token/` → `token/verify-totp/` → `{"access", "refresh"}`
(`djangorestframework-simplejwt`), `token/refresh/` — штатная вьюха
simplejwt без переопределений, `me/` — минимальный защищённый эндпоинт
(кому принадлежит текущий access-токен), заведён специально, чтобы было
что защищать в тестах/у реальных интеграций — без него нечем
подтвердить, что Bearer-токен вообще на что-то влияет. OpenAPI-схема —
`GET /api/v1/schema/`, Swagger UI — `/api/v1/docs/`
(`drf-spectacular`, `SpectacularAPIView`/`SpectacularSwaggerView`).

`SESSION_LOGIN`/`SESSION_LOGOUT` в WORM-аудите пишутся из ОБОИХ
контуров — событие означает «пользователь вошёл», не буквально «создана
Django-сессия» (само событие в `AuditLog.EventType` заведено ещё на
Этапе 1, но ничего его не писало до этой партии).

**Одно и то же сообщение** на неверный табельный номер / неверный
пароль / заблокированного пользователя (`authenticate()` через
`ModelBackend` сам отсекает `is_active=False`) в обоих контурах — не
даём внешнему наблюдателю понять, какая часть данных неверна или
существует ли такой табельный номер вообще.

**Честные границы (не реализовано, не должно приниматься за готовое):**
- **Rate limiting / lockout** на подбор пароля или TOTP-кода — реализован
  (Этап 3, см. «Анти-фрод» ниже), эта строка была честным пробелом до
  него.
- **`password_change_required` — реализовано** (по замечанию ревью, см.
  «Принудительная смена пароля» ниже) — больше не информационный флаг.
- **Админ-сценарий сброса TOTP — реализован** (по замечанию ревью, см.
  «Шифрование и сброс TOTP» ниже).
- **`totp_secret` шифруется отдельным ключом — реализовано** (по
  замечанию ревью, см. «Шифрование и сброс TOTP» ниже).
- **JWT blacklist — реализован** (по замечанию ревью, см. «JWT
  blacklist» ниже).
- **SRI-хэши для CDN htmx/Alpine.js в `templates/base.html`** не
  проставлены — не подтверждены вживую в этой сессии, чтобы не
  фабриковать неверные значения (сломали бы загрузку скриптов вместо
  того, чтобы её защитить). Проставить перед продом.

### Шифрование и сброс TOTP (по замечанию ревью)

**Шифрование** (`apps/iam/totp_crypto.py`, `cryptography.fernet.Fernet`)
— закрывает честную границу «`totp_secret` хранится в открытом виде».
Ключ — отдельная настройка `TOTP_ENCRYPTION_KEY` (небезопасное
dev-значение по умолчанию, тот же паттерн, что и у `SECRET_KEY`), **не
совпадает с `DJANGO_SECRET_KEY`** — компрометация одного не должна
автоматически раскрывать другой.

**Переходная миграция данных, не разрушающая существующие секреты**:
`User.totp_secret` (поле) переименовано в `totp_secret_plaintext`
(`RenameField`, не `RemoveField`+`AddField` — сохраняет уже
существующие открытые секреты при выкатке в прод), добавлено новое
`totp_secret_encrypted`. Свойство `User.totp_secret` (не поле) —
прозрачный доступ для всего остального кода (`apps/iam/totp.py`,
`services.py`, все существующие тесты) без единого изменения на
стороне вызывающих: геттер предпочитает `totp_secret_encrypted`, при
его отсутствии читает `totp_secret_plaintext` (запасной путь для
учёток, ещё не прошедших миграцию); сеттер всегда пишет только в
`totp_secret_encrypted`, `totp_secret_plaintext` обнуляет. Django
позволяет `@property` на модели участвовать в конструкторе
(`User(totp_secret=...)`) точно как обычное поле (`Options._property_names`)
— ни один из вызывающих кодов, ни один тестовый фикстур не потребовал
правки под рефакторинг, кроме одного места: `start_totp_enrollment()`
раньше писал `user.save(update_fields=["totp_secret"])` — это больше не
имя поля, исправлено на `update_fields=["totp_secret_encrypted", "totp_secret_plaintext"]`.

Одноразовая идемпотентная management-команда
`encrypt_totp_secrets` — переносит уже существующие
`totp_secret_plaintext` в `totp_secret_encrypted` (запускается один раз
при выкатке этой партии на среду с уже накопленными пользователями;
повторный запуск не находит кандидатов и ничего не делает). Само поле
`totp_secret_plaintext` не удаляется этой партией — отложено на
следующую миграцию, после того как команда фактически прогнана на
проде (см. её docstring).

**Административный сброс 2FA** (`UserAdmin.reset_totp`, action в
Django admin) — закрывает честную границу «нет сценария для
пользователя, потерявшего устройство»: обнуляет
`totp_secret_encrypted`/`totp_secret_plaintext`, `totp_enabled = False`
— пользователь заново проходит `start_totp_enrollment()`/
`confirm_totp_enrollment()` при следующем входе. Пишет новую WORM-запись
`AuditLog.EventType.USER_TOTP_RESET` (кто сбросил, кому) — тот же
принцип, что и у `USER_ROLE_CHANGED`: действие администратора над чужой
учётной записью обязано быть в аудите.

### JWT blacklist (по замечанию ревью)

`rest_framework_simplejwt.token_blacklist` подключён (`INSTALLED_APPS` +
его собственные миграции) — закрывает честную границу «logout не
отзывает уже выданные токены». `SIMPLE_JWT["BLACKLIST_AFTER_ROTATION"] = True`
— при каждом обновлении access через `token/refresh/` (уже
`ROTATE_REFRESH_TOKENS = True`) предыдущий refresh автоматически уходит
в чёрный список, не только явный logout. Новый эндпоинт
`apps.iam.api.LogoutView` (`POST /api/v1/auth/logout/`,
`IsAuthenticated` — тот же дефолт `REST_FRAMEWORK`, что и у остальных
эндпоинтов) принимает refresh явно и блэклистит его
(`RefreshToken(...).blacklist()`), пишет `SESSION_LOGOUT` в WORM-аудит
тем же `services.record_session_logout()`, что и Web-контур.

Периодическая очистка истёкших записей blacklist —
`apps.iam.tasks.cleanup_expired_tokens` (Celery-задача, оборачивает
встроенную команду simplejwt `flushexpiredtokens`), `CELERY_BEAT_SCHEDULE`
в `config/settings/base.py` задаёт расписание (раз в сутки). **Честная
граница**: ни один процесс `celery beat` в проекте не запускается (ни в
`docker-compose.yml`, ни в `deploy/` — только `celery worker`) — запись
расписания сейчас ничего не запускает сама по себе, задача вызывается
только вручную/из тестов, тот же честный разрыв, что у
`AUDIT_LOG_EXPORTED` (`apps/audit/models.py`).

**Честная граница, оставшаяся и после blacklist**: он покрывает только
refresh-токены. Access-токен, предъявленный после logout, продолжает
проходить `JWTAuthentication` до истечения своего TTL (15 минут,
`ACCESS_TOKEN_LIFETIME`) — простая JWT-аутентификация blacklist не
проверяет на каждый запрос (это стоило бы отдельного похода в БД на
каждый защищённый эндпоинт). Короткий TTL — единственная защита в этом
окне, как и было до этой партии.

### Принудительная смена пароля (по замечанию ревью)

Закрывает парную честную границу: `status = PASSWORD_CHANGE_REQUIRED` и
`User.is_password_expired` (365-дневный срок) были **только
информационными флагами** — ни один эндпоинт их не проверял, потому что
в проекте не было ни одной вьюхи смены пароля. Обе закрываются одним
и тем же механизмом, т.к. обе означают одно и то же требование
«пользователь обязан сменить пароль, прежде чем продолжить».

`apps.iam.views.PasswordChangeView` (Web-only, `GET`/`POST
/accounts/password/change/`) — первая и единственная вьюха смены пароля
в проекте. Форма — `apps.iam.forms.PasswordChangeForm`, наследует
`django.contrib.auth.forms.PasswordChangeForm` (текущий пароль +
`validate_password()` через уже существующие `AUTH_PASSWORD_VALIDATORS`,
включая `SpecialCharacterValidator`/`PasswordHistoryValidator`) — при
сохранении снимает `status = PASSWORD_CHANGE_REQUIRED` обратно на
`ACTIVE`, если он был выставлен (на `is_password_expired` влияет
косвенно — `User.save()` уже обновляет `password_changed_at` при любой
реальной смене хэша). `update_session_auth_hash()` — без него сессия
была бы инвалидирована следующим же запросом (Django привязывает её к
хэшу пароля), разлогинив пользователя сразу после того, как он
выполнил требуемое действие.

`apps.iam.middleware.PasswordChangeRequiredMiddleware` — на каждом
аутентифицированном Web-запросе редиректит на `password/change/`, если
`status == PASSWORD_CHANGE_REQUIRED` или `is_password_expired`.
**Явный allowlist префиксов** (`/accounts/`, `/admin/`, `/api/`), не
только сама страница смены пароля — иначе пользователь с этим статусом
не смог бы даже выйти (`logout/`) или пройти `login/verify-totp/`.
**Web-only, осознанно** — по формулировке ревью и по уже установленному
в проекте разделению контуров (`services.user_auth_summary()` возвращает
`password_change_required` как флаг в обоих контурах, но принудительный
редирект есть только в Web): External API — токен-контур для внешних
интеграций, у него нет понятия «текущая страница», принуждение к смене
пароля посреди программного цикла интеграции обрушило бы её без
предупреждения; там `password_change_required` остаётся тем же
информационным флагом, что и раньше — обработка на стороне
интеграции, не сервера.

### apps/documents — рабочее место «Реестр и карточка НРД» (ТЗ 4.1, 4.2)

Первое собственное рабочее место проекта. До этой партии карточки НРД
существовали только в Django admin — в README она была честно помечена
как «временный интерфейс до появления рабочих мест из ТЗ 4.1». Теперь
есть свой Web-контур: `/documents/` (реестр с фильтрами и постраничной
навигацией) и `/documents/<uuid>/` (карточка). Админка остаётся —
но уже не как единственный вход, а как инструмент администратора.

Структура — по конвенции, объявленной выше: `permissions.py` (правила
доступа), `forms.py` (валидация ввода), `views.py` (тонкий HTTP-слой),
`urls.py`. `api.py` для этого домена не заводился намеренно: внешнего
потребителя карточек НРД в ТЗ пока нет (External API закрывает вход и
Smart Search), а пустой файл под конвенцию — та самая преждевременная
абстракция, от которой оговорка выше и предостерегает.

**`permissions.py` — единый слой прав, которого в проекте не было.**
Правила доступа к НРД жили внутри `NormativeDocumentAdmin._can_access`
и `TemplateAdmin._can_manage`. Пока интерфейс был один, этого хватало;
со вторым потребителем дублирование гарантированно разъехалось бы —
поэтому правила вынесены в модуль, а `admin.py` теперь вызывает те же
функции (`visible_documents()`, `can_view_document()`), а не свои копии.

Матрица полномочий **выведена, а не процитирована**: поимённого
распределения операций над НРД по ролям в переданных материалах ТЗ нет.
Источники вывода перечислены в docstring модуля — прежний код админки
(ограничение по ДСП, круг правящих ролей), STACK.md (юридически значимое
действие за Контролёром/Юристом) и позиция «Методиста подразделения» в
`ROLE_PRIVILEGE_ORDER` (между Читателем и Контролёром — значит готовит
документы, но не придаёт им силу). Итог:

| Операция | Кто |
|---|---|
| Просмотр карточки без грифа | любой аутентифицированный |
| Просмотр карточки «ДСП» | `dsp_access` (признак учётной записи, не роль) |
| Редактирование **черновика** | Методист, Контролёр/Юрист, Администратор |
| Редактирование документа в силе | никто — только новая редакция со связью версионности (ТЗ 4.2.2) |
| Смена статуса (публикация/отмена/архив) | Контролёр/Юрист, Администратор |

**Это интерпретация и она требует подтверждения Заказчиком.** Спорные
места правятся в одном файле, без прикосновения к вьюхам и админке —
тесты `apps/documents/tests/test_permissions.py` фиксируют матрицу как
контракт и должны меняться вместе с ней.

Два следствия, которые стоит держать в голове:

- **ДСП — признак учётной записи, а не уровень роли.** Контролёр/Юрист
  без `dsp_access` документ с грифом не видит; Читатель с допуском —
  видит. Допуск оформляется отдельно от должности, и наследовать его от
  «старшинства» роли было бы прямым нарушением режима.
- **Право редактировать не наследуется вверх по статусу.** Документ,
  уже имеющий силу, не правится на месте ни одной ролью, включая
  Администратора: изменение оформляется новой редакцией и связью
  версионности (ТЗ 4.2.2). Иначе история статусов (ТЗ 4.2.3) описывала
  бы документ, которого никогда не существовало в таком виде.

**Адресация по UUID, а не по регистрационному номеру.** `reg_number` в
модели покрыт индексом, но **не ограничением уникальности** — номер
«12-п» может встречаться у документов разных лет и разных подразделений.
Красивый ЧПУ `/documents/12-п/` в общем случае адресовал бы не одну
карточку, а несколько, поэтому маршрут построен на `<uuid:pk>`.

**Документ «ДСП» без допуска отдаёт 404, а не 403.** 403 подтвердил бы
существование документа с этим идентификатором — тот же принцип
неразличимости ответов, что уже применён к форме входа (одинаковое
сообщение на неверный табельный номер и на неверный пароль).

**Гриф проверяется и в графе связей.** Карточка показывает связи
версионности, а связанный документ тоже может быть под грифом. Без
фильтрации ДСП обходился бы «сбоку»: номер и наименование закрытого
документа утекли бы в карточку соседнего, открытого. Поэтому связи
пропускаются через тот же `visible_documents()`.

**Найденная ошибка вёрстки — честная граница шаблонов.** При визуальной
проверке в браузере выяснилось, что в шапке (`templates/base.html`)
несколько релизов висел видимый служебный текст: `{# … #}` в Django —
комментарий **однострочный**, многострочный блок этим синтаксисом не
вырезается и попадает в ответ как текст. Затронуты были заметки про
SRI-хэши и про роль в личном кабинете. Все многострочные комментарии
переведены в `{% comment %}…{% endcomment %}`, добавлена регрессия
(`TemplateCommentRenderingTests`), которая проверяет отрендеренные
страницы, а не файлы шаблонов. Урок для проекта: `assertContains`
проверяет наличие нужного, но никогда — отсутствие лишнего; UI-партии
имеет смысл хотя бы раз открывать глазами.

**Границы партии 1 (сняты партией 2, ниже):** реестр и карточка были
только на чтение. `forms.py` импортирует `apps.iam.models.Department`
напрямую (для фильтра по издавшему подразделению) — так же, как это
делает `models.py` того же приложения: FK на подразделение уже часть
схемы домена, отдельного анти-коррупционного слоя под него не вводилось.

### Запись НРД: создание, правка, смена статуса (партия 2 Этапа 2)

Маршруты: `/documents/new/`, `/documents/<uuid>/edit/`,
`/documents/<uuid>/status/`. Слои — `services.py` (единственное место
записи), `transitions.py` (граф статусов), `forms.py`
(`DocumentForm`/`StatusChangeForm`), `views.py` (только HTTP).

**Главная находка партии: SCD-2 не велась вообще.** Модель
`DocumentStatusHistory`, exclusion constraint `EXCLUDE USING gist` и
вывод истории в карточке существовали с Этапа 1 — а писать в таблицу
было некому. Единственным её потребителем были собственные тесты
ограничения. То есть требование ТЗ 4.2.3 было закрыто схемой, но не
поведением: у любого документа история статусов оставалась пустой
навсегда.

Теперь срезы ведёт `NormativeDocument._sync_status_history()`:
- создание карточки открывает первый срез `[сейчас, NULL)` со статусом
  «Черновик»;
- смена статуса закрывает текущий срез и открывает новый **той же самой
  отметкой времени** — `[t0, t1)` и `[t1, NULL)`. Границы `tstzrange`
  полуоткрыты, поэтому пересечения нет, а двух соседних отметок нарочно
  не используется: между ними образовалась бы дыра, в которой у
  документа формально не было никакого статуса.

**Почему синхронизация в `save()`, а не только в сервисе.** Аудит смены
статуса (усиление аудита, решение Заказчика) уже жил в `save()`. Статус
меняет не только Web GUI: есть админка, импорт, management-команды.
Веди историю отдельный шаг сервиса — эти пути писали бы аудит без
истории, и два журнала одного и того же события разошлись бы. Это ровно
та беда, от которой в партии 1 спасли вынесением прав в один модуль.
Блокировка строки (`select_for_update`) при этом осталась за сервисом:
она нужна вокруг «прочитать статус → проверить переход → записать», а
это уже не дело метода `save()`.

Соответственно снято устаревшее предупреждение в docstring
`DocumentStatusHistory` («сервис… Этап 2, пока не реализован») и
уточнён `ConcurrentStatusTransitionTests`: он намеренно обходит сервис и
пишет в историю напрямую — проверяет последний рубеж, ограничение БД,
которое обязано держать и там, куда блокировка не дошла.

**Граф переходов (`transitions.py`) — снова вывод, а не цитата.**
Перечень статусов задан ТЗ, допустимые переходы между ними — нет:

```
Черновик        → Действует | Архив
Действует       → Действует с изм. | Утратил силу
Действует с изм.→ Утратил силу
Утратил силу    → Архив
Архив           → (терминальное состояние)
```

Чего в графе нет намеренно: возврата `Действует → Черновик` (снятие
силы — это «Утратил силу», иначе история описывала бы документ, который
побыл действующим, не будучи отменённым); прямого
`Действует → Архив` (действующий документ в архив не сдаётся). Переход
`Черновик → Архив` добавлен для отклонённого черновика: удаления в
системе с WORM-журналом нет, и без него такая карточка висела бы в
реестре вечно. **Требует подтверждения Заказчиком**, тесты
`test_transitions.py` фиксируют граф как контракт; отдельный тест
проверяет, что каждый статус модели в графе присутствует — иначе новый
статус молча стал бы тупиком.

**Проверка ацикличности при публикации — дословное требование ТЗ 4.2.2.**
Каждое ребро уже проверяется при создании (`DocumentRelation.clean()`),
поэтому в норме цикла быть не может. Но требование ТЗ относится именно к
публикации, а пути в обход `clean()` существуют — сырой SQL, миграции
данных. Поэтому `change_document_status()` при переходе в «Действует»
делает один рекурсивный запрос (`find_cycle_through_document()`) и
отказывает, называя документ, на котором цикл замыкается. На переходах,
не придающих силу, проверка не выполняется сознательно: иначе цикл,
попавший в базу в обход валидации, намертво запер бы карточку — её нельзя
было бы даже отменить.

**Что ещё нашла живая проверка в браузере.** Как и в партии 1, страницы
открывались глазами, и это снова окупилось:

- `django.contrib.messages` был подключён в настройках с Этапа 1, но
  **ни один шаблон его не выводил** — все `success`/`error` молча
  терялись. Добавлен компонент `.notice` и вывод в `base.html`.
- `select[multiple]` с классом `.field` обрезал последнюю строку:
  вертикальный padding съедал её высоту, и список подразделений
  выглядел разрезанным посередине названия.
- В подсказке поля «Дата рассекречивания» наружу торчало имя поля БД
  (`не от reg_date`) — заменено на «а не от даты регистрации»
  (миграция `0007`, изменение `help_text`).

Ни один из трёх дефектов не виден автотестам: страницы отдавали 200,
все `assertContains` проходили.

**Оставшиеся границы партии 2:**

- **Связи версионности заводятся только через админку.** Карточка их
  показывает, но UI создания ребра графа в Web GUI нет — а «Отменяет»/
  «Принят взамен» это то, чем методист пользуется постоянно. Ближайший
  кандидат в следующую партию.
- **Правка не ведёт истории изменений полей.** В WORM-журнал попадает
  смена статуса и смена категории хранения, но не «кто и когда исправил
  наименование черновика». Для черновика это терпимо, для полноты
  ТЗ 4.7 — нет.
- **`api.py` для домена по-прежнему не заведён** — внешнего потребителя
  карточек НРД в ТЗ нет, а сервисный слой уже готов принять второй
  контур без переписывания.
- **Формат даты в `<input type="date">` задаёт локаль браузера, не
  приложение.** В песочнице поля показывают `mm/dd/yyyy`; на рабочем
  месте с русской локалью будет `дд.мм.гггг`. Сервер на это повлиять не
  может — отмечено, чтобы при приёмке это не приняли за дефект вёрстки.

### Завершение Этапа 2: связи, банк бланков, журнал аудита, личный кабинет

Три партии, закрывающие остаток рабочих мест ТЗ 4.1–4.3 и 4.7.

**Связи версионности в Web GUI (ТЗ 4.2.2).** Рёбра графа заводились
только через Django admin — при том, что «Отменяет»/«Принят взамен»
методист проставляет постоянно. Теперь `/documents/<uuid>/relations/new/`
и снятие связи POST-запросом из карточки.

Права вынесены в `permissions.can_manage_relations()`. Круг ролей тот же,
что у правки, но **статус документа здесь не ограничивает**, в отличие от
`can_edit_document`: связь описывает отношение между двумя карточками, а
не содержание одной. «Отменяет 87-р» заводится на новом документе, пока
он черновик, — а забытую ссылку на смежный НРД приходится дописывать и к
уже действующему. Запрет по статусу означал бы, что единственный способ
исправить граф после публикации — админка.

Отдельно проверяется видимость **цели** связи: ссылку на документ,
которого пользователь не видит, завести нельзя, иначе гриф «ДСП» утекает
через сам факт успешного создания связи. Выпадающий список целей тоже
строится из `visible_documents()` и без самой карточки.

Таблица связей не WORM — ошибочное ребро надо уметь снять, — поэтому
заведены **оба** события журнала: `DOCUMENT_RELATION_ADDED` и
`DOCUMENT_RELATION_REMOVED`. Снятие связи меняет граф, по которому
документ считается отменённым, и бесследным быть не должно.

Попутно найдено тестом: наружу лезли английские имена полей. Подпись
формы читалась «Relation type», а сообщение о дубле — «поля From
document, To document и Relation type уже существует». Причина — у
`DocumentRelation` не было `verbose_name`, и Django подставлял имена
атрибутов. Добавлены `verbose_name` всем трём полям и
`violation_error_message` самому `UniqueConstraint` (миграция `0008`).

**Банк бланков (ТЗ 4.3).** `/templates/` — список семейств форм с
действующей версией, `/templates/<uuid>/` — линия версий, выпуск новой
версии, скачивание. До этой партии банк форм существовал только в
админке, из которой линейный сотрудник не мог даже скачать действующий
бланк — то есть операция, ради которой банк и заводится, интерфейса не
имела.

Правки выпущенной версии нет и быть не может: ТЗ 4.3.1 требует
инкремента версии даже для минорной корректировки, поэтому
`services.publish_version()` только выпускает новую строку, переводит
предыдущую активную в `superseded` и связывает их в обе стороны.
Семейство берётся под `select_for_update()`: без блокировки две
одновременные публикации обе увидели бы одну и ту же «текущую активную»
версию, и предыдущая получила бы два `superseded_by`.
`UniqueConstraint(family, version)` такую гонку не ловит — версии-то
разные.

**Закрыта ещё одна «заготовка» журнала:** `ARCHIVE_DOWNLOAD` был заведён
в модели с Этапа 1, но его не писал никакой код. Теперь скачивание
заменённой версии бланка попадает в журнал, а `download_count` растёт
через `F()` — чтение-запись в Python потеряло бы одно из двух
одновременных скачиваний. Файл отдаётся приложением, а не прямой ссылкой
в хранилище: иначе и счётчик, и запись о выдаче архивной формы
обходились бы копированием ссылки. Имя поля файла в адресе ограничено
конвертером маршрута двумя допустимыми значениями.

**Журнал аудита (ТЗ 4.7).** `/audit/` — фильтры по типу события,
табельному номеру, объекту и периоду. Журнал вёлся с Этапа 1, но
прочитать его можно было только в Django admin: Офицеру ИБ требовался
`is_staff`, а сама роль на доступ к журналу не влияла никак.

Доступ — Офицер ИБ и Администратор. **Контролёр/Юрист намеренно не
включён**: он выше Методиста по документам, но журнал показывает в том
числе его собственные действия, и «проверяющий, читающий журнал своих
действий» — это не разделение обязанностей. Как и прочие матрицы прав в
проекте, **требует подтверждения Заказчиком**.

Страница только читает и ничего не предлагает менять: журнал WORM, и
интерфейс не должен намекать на обратное. Пункт меню показывается по
тому же `can_view_audit_log`, что закрывает вьюху — через
контекст-процессор, иначе меню и вьюха разъехались бы, и пользователь
видел бы ссылку в 404.

**Личный кабинет (п.8.2 решения Заказчика).** `/accounts/profile/`:
роль, допуск ДСП, состояние 2FA, срок действия пароля и последние
десять собственных входов. До этого единственным местом во всём Web GUI,
где пользователь видел себя, была строка в шапке — при том, что система
ограничивает его и по сроку пароля, и по 2FA, и по допуску.

Срок пароля считается по той же константе `PASSWORD_EXPIRY_DAYS`, что и
`User.is_password_expired`: иначе кабинет показывал бы одну дату, а
middleware перенаправлял на смену пароля в другую.

**Что нашла живая проверка в браузере на этот раз.** Журнал аудита
отдавал 200, все `assertContains` проходили — а на экране одна запись
импорта тезауруса выбрасывала в таблицу сотни терминов и вырастала выше
всей остальной страницы, хороня под собой сам журнал. Значения реквизитов
обрезаны, полное доступно подсказкой; добавлен регрессионный тест на
отрендеренную страницу.

**Оставшиеся границы Этапа 2:**

- **Правка карточки не пишется в журнал пополнительно.** Смена статуса,
  категории хранения и связи фиксируются; «кто исправил наименование
  черновика» — нет.
- **Экспорта журнала аудита нет ни в одном контуре**, поэтому событие
  `AUDIT_LOG_EXPORTED` остаётся единственной незакрытой «заготовкой»
  модели журнала.
- **`api.py` не заведён ни для `documents`, ни для `templates_bank`** —
  внешнего потребителя в ТЗ нет, а сервисные слои готовы принять второй
  контур без переписывания.
- **У бланка нет грифа «ДСП»** — в модели `Template` такого поля не
  существует. Это свойство схемы, а не упущение слоя прав: если Заказчик
  потребует закрытых форм, поле придётся заводить в модели.
- **Личный кабинет доступен при `password_change_required`** — он под
  уже существующим exempt-префиксом `/accounts/`, введённым, чтобы
  пользователь мог выйти и пройти 2FA. Страница только читает, но
  формально это исключение из принуждения к смене пароля.
- **Формат `<input type="date">` задаёт локаль браузера**, не
  приложение.

### Уточнения Заказчика: жизненный цикл НРД и доступ к журналу

Две матрицы, помеченные в Этапе 2 как выведенные и требующие
подтверждения, Заказчик рассмотрел и уточнил. Ниже — что изменилось и
почему; исходные формулировки в `transitions.py` и
`apps/audit/permissions.py` приведены в соответствие.

**Ошибочная публикация оформляется двумя разными путями, а не одним.**
Прежний граф оставлял единственный выход — «Утратил силу», а он
утверждает, что документ действовал и перестал. При ошибке публикации
(не тот файл, не та дата, преждевременный выпуск) это неправда: документ
не должен был действовать вовсе, и такая запись искажает юридическую
историю в системе, которая ведётся именно ради юридической значимости.
Теперь:

| Переход | Смысл |
|---|---|
| `Действует → Черновик` | **Откат**: публикация преждевременна, документ вернётся в работу и будет издан заново |
| `Действует → Аннулирован` | **Аннулирование**: публикация признана недействительной, документ в работу не возвращается |
| `Действует → Утратил силу` | документ действовал и перестал — как и раньше |

`Аннулирован` — новый статус модели (миграция `0010`), а не синоним
отмены. В истории статусов период «Действует» у аннулированного
документа остаётся: он фиксирует сам факт ошибки, но силы документ не
имел.

**Оба перехода оставлены Администратору и требуют основания.** Публикует
Контролёр/Юрист — и он же не должен бесследно исправлять собственную
ошибку: это разделение обязанностей, тот же принцип, по которому журнал
аудита закрыт от него самого. Основание обязательно, потому что запись
«публикация отменена» без объяснения бесполезна и проверяющему, и
подразделению через полгода. Проверяется дважды — формой и сервисом:
форму можно обойти прямым запросом.

Список переходов в форме фильтруется по роли: Контролёру/Юристу откат и
аннулирование не предлагаются вовсе — предлагать заведомый отказ значит
делать плохой интерфейс.

**Отдельные типы событий журнала.** `DOCUMENT_PUBLICATION_ROLLED_BACK` и
`DOCUMENT_ANNULLED` вместо общего `DOCUMENT_STATUS_CHANGED`: это ровно те
записи, которые проверяющий ищет в первую очередь, и находить их
фильтром «изменён статус» вперемешку с рутиной значит не находить.
Откат при этом отличается не новым статусом, а тем, ОТКУДА он:
«Действует → Черновик» — исправление ошибки, а первое сохранение
черновика — нет.

**`Действует с изм. → Действует`.** Если все изменяющие документы
отменены, базовый снова действует в исходной редакции. Ситуация обычная,
а выхода из «Действует с изм.» кроме утраты силы раньше не было. Решение
принимает Контролёр/Юрист, как и любую смену статуса.

**Доступ к журналу: история действий на карточке.** Полный журнал
остался Офицеру ИБ и Администратору (Контролёр/Юрист по-прежнему не
включён — журнал показывает в том числе его собственные действия). Но
на карточке НРД появился раздел «История действий по документу»: кто
опубликовал, кто отменил, кто менял связи и с каким основанием. Он
видим всем, у кого есть доступ к карточке, потому что это не контроль
безопасности, а обычная работа — до этого Методист не мог узнать, кто
опубликовал его же приказ, иначе как через Офицера ИБ.

**Побочно исправлен ключ журнала по НРД.** Записи по карточкам
ключевались `reg_number`, который **не уникален** (только индекс), — при
том что бланки и учётные записи уже ключевались по `pk`. НРД был
единственным исключением, и раздел «История действий» на нём немедленно
показал бы события чужой карточки с тем же номером. Теперь `object_id`
это UUID, а рег. номер остался в реквизитах события снимком на момент
записи.

Следствия, которые пришлось учесть:

- **Журнал WORM — старые записи переписать нельзя.** Раздел на карточке
  ищет и по UUID, и по рег. номеру: совпадение по номеру может
  принадлежать однофамильцу, и это честная цена обратной совместимости,
  уменьшающаяся сама по мере накопления новых записей.
- **Фильтр «Объект» в журнале** ищет и по идентификатору, и по
  `details.reg_number`: человек вводит номер документа, который у него
  на руках, а не UUID.
- **Отклонённая загрузка** (антивирус, макросы) вообще не оставляет
  строки в БД, и UUID там указывает в пустоту. Поэтому
  `antivirus.scan_uploaded_field()` и `macro_check.reject_if_has_macros()`
  принимают `object_label` — человекочитаемый ярлык (рег. номер НРД,
  семейство и версия бланка), который попадает в реквизиты события.

**Тесты.** `test_status_audit.py` сравнивал словарь реквизитов целиком —
такое сравнение падает от любого дополнения состава и ничего не говорит
о проверяемом поведении; переведён на проверку по ключам. В
`test_permissions.py` появился помощник `login_client()`: Администратору
2FA обязательна, и middleware политики учётной записи уводит его на
подключение фактора с любой страницы — без этого тест на действие
Администратора проверял бы редирект, а не само действие.

## Доменные события (`apps/core/domain_events.py`)

Внутрипроцессная шина: `publish(event_name, **payload)` +
`@register(event_name)`. Побочные эффекты, выходящие за границу
изменяемой записи, вынесены из тел `save()` в обработчики
(`apps/iam/handlers.py`, `apps/audit/handlers.py`, подключаются из
`AppConfig.ready()`).

**Зачем, если Django-сигналы уже есть.** Сигналы `pre_save`/`post_save`
дают только «объект сохранён», без того, ЧТО именно изменилось: чтобы
отличить «роль поменяли» от «поменяли что-то ещё», подписчику пришлось бы
самому перечитывать прошлое состояние из БД — ровно ту работу, которую
`save()` уже сделал. Здесь событие несёт готовую разницу
(`previous_role`/`new_role`, `previous_password_hash`), а имена событий —
доменные («роль повышена»), не ORM-ные («модель сохранена»).

**Главное — это способ соблюсти доменные границы.** README объявляет
модульный монолит, где приложения не импортируют друг друга напрямую.
`User.save()` и `import_personnel()` больше не пишут в
`apps.audit.models.AuditLog` сами: они публикуют `user.role.changed` /
`user.role.elevated`, а в WORM-журнал пишет обработчик внутри
`apps/audit`. Для этих событий направление зависимости перевёрнуто —
аудит знает про события IAM, IAM про аудит не знает.

**Честная граница: перевёрнута пока только часть.** Остальной аудит
`apps/iam` (вход/выход, неудачные попытки входа, сброс 2FA админом —
`services.py`, `admin.py`) по-прежнему обращается к `AuditLog` прямым
импортом, около двух десятков мест. Событийная шина применена там, где
она попутно решала конкретную задачу (вынос побочных эффектов из
`save()`); переводить на неё разом весь аудит IAM в этой партии не
стали — это отдельная задача с собственным набором событий, а не
побочный эффект уборки в `save()`.

**`publish()` — синхронный, в текущей транзакции.** Не `on_commit`:
запись в WORM-журнал и история паролей обязаны быть атомарны со сменой
состояния, откат транзакции обязан откатывать и их. Исключение
обработчика намеренно пробрасывается наверх — упавший аудит должен
ронять операцию, а не тихо теряться. Для некритичных потребителей есть
отдельный `publish_after_commit()` (там исключение, наоборот, гасится в
лог: коммит уже состоялся, откатывать нечего).

**Честная граница — тихий отказ при обрыве подписки.** Если импорт
модуля обработчиков из `AppConfig.ready()` пропадёт, события продолжат
публиковаться «в пустоту»: операция пройдёт успешно, а аудит и история
паролей молча перестанут писаться. Тесты доменной логики такой обрыв не
ловят (они проверяют результат, а не наличие подписки), поэтому заведён
отдельный набор `apps/core/tests/test_domain_events.py`, который
проверяет сам факт регистрации каждого публикуемого события.

**Отдельно зафиксировано (регрессия, исправлена по итогам ревью):**
ранее `apps/iam/handlers.py` подменял метод целиком —
`User.save = _save_without_side_effects`. Тело `save()` в
`apps/iam/models.py` при этом оставалось на месте, выглядело рабочим,
имело подробные комментарии — и никогда не выполнялось; две копии одной
логики успели разойтись. Подмена снята, логика живёт в одном месте
(`User.save()` меняет состояние и публикует события), а
`apps/iam/handlers.py` только подписывается. Тест
`test_user_save_is_not_monkey_patched` не даёт этому вернуться.

## Троттлинг HTTP (`apps/core/limits.py`, `apps/core/drf_throttles.py`)

Счётчик фиксированного окна поверх `django.core.cache`
(`consume_fixed_window`), поверх него — базовый DRF-класс
`FixedWindowThrottle` и конкретные лимиты: `apps/iam/throttles.py`
(token-obtain 60/мин, totp-verify 60/мин, token-refresh 120/мин, me
300/мин), `apps/search_ocr/throttles.py` (поиск 30/мин), плюс
per-view-лимиты Web-контура в `apps/iam/views.py` (60/мин). Поиск —
единственный лимит заметно ниже остальных: его запрос дороже (расширение
по тезаурусу + три FTS-поля на термин), см. раздел Smart Search выше.

**Это НЕ дубль блокировки учётной записи.** Их две, разного назначения,
и они намеренно не сведены в одну:

- **Lockout по `AuditLog`** (`apps/iam/services.py`, 5 неудачных попыток
  / 15 мин на табельный номер + 20 / 15 мин на IP) — контроль подбора
  пароля/TOTP. Считает только НЕУДАЧНЫЕ попытки, живёт в БД, переживает
  перезапуск процесса, не зависит от Redis — см. «Анти-фрод» выше.
- **Троттлинг здесь** — защита HTTP-ресурсов от потока запросов
  (в том числе успешных). Считает ВСЕ запросы, живёт в кэше процесса,
  сбрасывается при перезапуске.

Лимиты намеренно подняты (Web-контур 8/12 → 60/мин, token-obtain
5 → 60/мин, totp-verify 10 → 60/мин): при первоначальных значениях они
срабатывали раньше собственно lockout'а и подменяли собой контроль
подбора — пользователь получал «слишком много попыток» вместо честной
блокировки учётной записи. В прогоне всего набора тестов те же низкие
пороги ещё и ложно блокировали соседние тесты: фикстуры по всему проекту
используют один и тот же табельный номер (`0001`) и один и тот же
клиентский IP, а счётчик — общий на процесс и между тестами не
сбрасывается.

**Честные границы:**
- Бэкенд кэша по умолчанию — `LocMemCache`, то есть счётчик **на
  процесс**: при нескольких воркерах gunicorn фактический лимит
  умножается на их число. Для защиты от потока это приемлемо, для
  контроля подбора — нет, и именно поэтому lockout считает по БД.
  Общий кэш (Redis) подключается настройкой `CACHES`, кода менять не
  придётся.
- Состояние глобально на процесс и не сбрасывается между тестами —
  тест, дергающий эндпоинт под троттлингом много раз, обязан либо
  чистить кэш, либо разводить identity (IP/табельный номер).

## Локальная разработка в этой сессии

**Хост-ОС песочницы — Ubuntu 24.04 LTS, это НЕ целевая платформа
развёртывания** (см. «Платформа развёртывания» выше — Debian 12
Bookworm) и никогда ей не была: песочница используется только для
запуска тестов/`manage.py` в процессе разработки, не для проверки
совместимости с продакшн-ОС. Приложение не привязано к хост-ОС напрямую
— Postgres/Redis/MinIO и т.д. в `docker-compose.yml` запускаются как
Docker-образы с зафиксированными версиями (работают одинаково что на
Ubuntu, что на Debian, важен только Docker, а не дистрибутив-хозяин), а
сам Django-код — чистый Python + pip-пакеты без системных зависимостей,
привязанных к конкретному дистрибутиву. Хост-ОС реально важна только для
**системных** пакетов (`psycopg[binary]`, `argon2-cffi` и т.п. под
Python 3.14, если он будет выбран) непосредственно на сервере Заказчика
— это и есть матрица совместимости на Debian 12/PGDG из раздела
«Платформа развёртывания», а не что-либо в этой песочнице.

Песочница, в которой велась разработка, не имеет доступа к пакетам
PostgreSQL 18 (в apt только 16-я ветка), к Python 3.14 (deadsnakes PPA
недоступен из контура) и к Docker Hub/Quay (нет демона Docker — образы
из `docker-compose.yml` не подтягивались и не проверялись «вживую», только
`docker compose config` на синтаксис). Проверка каркаса в этой сессии
проведена на:

- Python 3.13.12 (ближайшая доступная версия);
- PostgreSQL 16.13 (схема не использует возможностей, специфичных для
  PostgreSQL 17/18 — `tstzrange`, `EXCLUDE USING gist`, `btree_gist`
  поддерживаются начиная с PostgreSQL 9.2);
- Django 5.2.17, Gunicorn 23.0.0.

`manage.py check`, `manage.py migrate` (включая exclusion constraint по
ТЗ 4.2.3) и запуск под Gunicorn прошли чисто. Разделение хранилищ
проверено функционально: сохранённые `files_original`/`files_editable`
действительно оказываются в разных каталогах (`mediafiles/originals/` /
`mediafiles/working/`) — на локальном `FileSystemStorage`, аналог для
двух S3-бакетов в `config/settings/prod.py` не проверялся вживую (нет
доступа к MinIO/Docker в этой песочнице). Перед вводом в опытную
эксплуатацию необходимо повторить проверку на целевых версиях
PostgreSQL 18.6, подтверждённой версии Python (3.13 или 3.14.7 — см.
«Политика версий») и вживую поднятых образах
etcd/PgBouncer/ClamAV/Prometheus/Grafana/MinIO (включая сам
`init-bucket.sh` — создание бакета с `--with-lock`).

**Исключение — конвейер OCR (Этап 3)**: в отличие от Docker/MinIO-зависимых
частей выше, системные пакеты `tesseract-ocr`, `tesseract-ocr-rus`,
`poppler-utils` (через apt) и Redis-сервер устанавливаются и запускаются
в этой песочнице напрямую (не в Docker), поэтому конвейер проверен
по-настоящему **вживую end-to-end**, а не только описан: PDF, сгенерированный
на лету → `pdf2image`/poppler → `pytesseract`/Tesseract (язык `rus`) →
корректно распознанный текст и словарь уверенности по словам
(`apps/documents/tests/test_ocr.py` — тот же прогон воспроизводится в CI,
см. «Конвейер OCR» выше).
