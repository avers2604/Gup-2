## Политика версий: Django 5.2 LTS + Python

Официально Django 5.2 LTS поддерживает Python 3.10–3.13 (на момент выхода
релиза 3.14 ещё не существовал; официальная поддержка более новых веток
добавляется точечными релизами Django, но заранее не гарантирована). Из
этого следует прямая связка версий, а не два независимых решения:

- **Фреймворк: Django 5.2 LTS**, зафиксирован. В ветке 5.2 разрешены
  только минорные и патч-обновления (`5.2.x`); переход на следующую
  мажорную версию Django — только отдельным согласованным решением, не
  попутно с другой задачей.
- **Python: связка с Django, а не независимый выбор.**
  - `3.14.7` — candidate target (версия из исходного списка Заказчика);
  - `3.13.x` — validated fallback / текущий базовый вариант (то, на чём
    реально проверен весь код в этом репозитории);
  - итоговое решение принимается **до конца Этапа 1** по результатам
    матрицы совместимости на целевой ОС (Astra Linux / РЕД ОС / Ubuntu
    22.04+): наличие пакетов/колёс для `psycopg[binary]`, `argon2-cffi`,
    `django-storages`/`boto3`, `gunicorn` под 3.14, и подтверждение, что
    сама связка Django 5.2 + Python 3.14 protестирована (официально или
    сообществом) на момент развёртывания.
  - Правило приоритета: **если 5.2 подтверждённо стабильно работает и на
    3.14 — можно рассмотреть повышение; в обратную сторону (понижение
    Python из-за проблем с Django) решение не пересматривается — тогда
    остаёмся на 3.13.**

Если Заказчиком версия Django 6.1 зафиксирована по внешней причине
(например, уже согласована с ОС-дистрибутивом/реестром пакетов Astra
Linux или РЕД ОС и завязана на другие компоненты), это отдельный повод
вернуться к 6.1 — тогда нужно явное подтверждение, что для 6.1
обеспечена поддержка минимум на срок эксплуатации до следующего
планового обновления. Требование `condition=` вместо устаревшего
`check=` у `CheckConstraint` (совместимо и с 5.2, и с 6.1) сохранено в
коде независимо от исхода этого решения.

В этой сессии код проверен на **Django 5.2.17 + Python 3.13.12** —
именно эта связка сейчас является рабочим базовым вариантом проекта.

## Лицензии и поддержка (требуют решения Заказчика/юридической службы)

- **Redis 8.x — лицензия AGPLv3** (Redis Ltd вернула Redis на открытую
  лицензию начиная с версии 8, после периода RSAL/SSPL у 7.4). Redis
  используется здесь только как отдельный инфраструктурный сервис по
  сети (очереди Celery), не встраивается и не модифицируется в составе
  продукта — при таком использовании риски полноценных copyleft-
  обязательств обычно ниже, чем при встраивании кода, но для
  государственного заказчика в любом случае нужно формальное
  заключение юридической службы, а не техническая оценка.
  Если заключение отрицательное, план Б — **Valkey** (форк Redis под
  BSD-3, поддержан Linux Foundation, протокол-совместим с Redis).
  Valkey рассматривается как функциональная замена только **после
  подтверждения совместимости с Celery-брокером и персистентным
  контуром очередей** (AOF-эквивалент, поведение при рестарте с
  накопленной очередью OCR/эскалаций) — это отдельная проверка перед
  переключением, не автоматическая замена по названию.
- **MinIO Community Edition — лицензия AGPLv3.** Решение — использовать
  community-редакцию (не коммерческую AIStor) с явным набором
  возможностей, требуемых ТЗ 4.9: Distributed mode, Erasure Coding,
  Object Locking / WORM, Versioning, контроль целостности по SHA-256
  (см. `docker-compose.yml` и поле `files_original_sha256` карточки НРД).
  Как и Redis, требует формального заключения юридической службы
  Заказчика о допустимости AGPLv3 в контуре предприятия — использование
  как отдельного сервиса по S3-протоколу (без модификации и
  распространения исходного кода MinIO) обычно не создаёт
  copyleft-обязательств для АИС «БЗ ГЭТ», но техническая оценка не
  заменяет юридическую.
- **ClamAV, Prometheus, Grafana, PostgreSQL, PgBouncer, etcd, nginx,
  pgBackRest, Tesseract** — постоянные открытые лицензии (GPLv2, Apache
  2.0/AGPLv3 для Grafana, PostgreSQL License, ISC/BSD и т.п.) без
  известных рисков для встраивания как инфраструктурных зависимостей;
  отдельного юридического ревью не требуют.

## Локальная разработка в этой сессии

Песочница, в которой велась разработка, не имеет доступа к пакетам
PostgreSQL 18 (в apt только 16-я ветка), к Python 3.14 (deadsnakes PPA
недоступен из контура) и к Docker Hub/Quay (нет демона Docker — образы
из `docker-compose.yml` не подтягивались и не проверялись «вживую», только
`docker compose config` на синтаксис). Проверка каркаса в этой сессии
проведена на:

- Python 3.13.12 (ближайшая доступная версия);
- PostgreSQL 16.13 (схема не использует возможностей, специфичных для
  PostgreSQL 17/18 — `tstzrange`, `EXCLUDE USING gist`, `btree_gist`
  поддерживаются начиная с PostgreSQL 9.2);
- Django 5.2.17, Gunicorn 23.0.0.

`manage.py check`, `manage.py migrate` (включая exclusion constraint по
ТЗ 4.2.3) и запуск под Gunicorn прошли чисто. Перед вводом в опытную
эксплуатацию необходимо повторить проверку на целевых версиях
PostgreSQL 18.6, подтверждённой версии Python (3.13 или 3.14.7 — см.
«Политика версий») и вживую поднятых образах
etcd/PgBouncer/ClamAV/Prometheus/Grafana/MinIO.
